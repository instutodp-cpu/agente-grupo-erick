# Hermes Agent Core - Validation Semantics and Architecture Gates

## Objetivo

Auditorias das PRs #98-#100 identificaram inconsistências semânticas de validação: flags como `authorization_validated`/`evidence_validated`/`bindings_validated`/`budget_validated`/`dependencies_validated`/`idempotency_validated`/`stop_conditions_validated`/`compensations_validated` eram hardcoded `true` em `execution-plan-engine.js`'s `buildOutcome()` e em `execution-authorization-boundary.js`'s `buildDecisionForRequest()`, **independentemente de qual etapa realmente bloqueou a avaliação** — um plano bloqueado em `BUDGET_BLOCKED` reportava `idempotency_validated: true` mesmo nunca tendo alcançado essa etapa. Separadamente, `EXECUTION_PLAN_STATUSES` nunca continha os literais `'EXECUTION_PLAN_PREPARED_SIMULATION'`/`'BINDING_BLOCKED'` mesmo o engine produzindo ambos desde as PRs #96/#98, colapsando silenciosamente todo plano nesses estados para `VALIDATION_FAILED` em `buildExecutionPlanContract`. E `npm test`'s lista de arquivos mantida manualmente já havia esquecido `test/execution-reference-binding-provenance.test.js` (87 testes da PR #100) — nunca executado sob `npm test`, só sob invocação direta.

Esta PR corrige as três classes de defeito e cria gates automáticos de arquitetura para impedir que qualquer uma delas volte a acontecer: **estados de validação progressivos e explícitos** (substituindo flags binárias enganosas), **preservação de status específico** entre contrato/engine/resultado (nunca colapsar silenciosamente para `VALIDATION_FAILED`), **descoberta automática de testes** (nenhum arquivo de teste pode ser esquecido pelo `npm test` novamente), e **21 gates de arquitetura** que rodam em CI antes da suíte de testes completa.

**VALIDATED ≠ READY ≠ AUTHORIZED ≠ EXECUTABLE ≠ EXECUTION_STARTED ≠ EXECUTED.** Mesmo no melhor cenário possível desta PR — `validation_pipeline_completed=true`, `architecture_gates_passed=true`, `references_bound_in_simulation=true`, `execution_plan_prepared=true` — `executable`, `execution_authorized`, e `execution_started` permanecem `false`; todo flag operacional (`stage_started`, `tool_called`, `workflow_executed`, `provider_called`, `model_called`, `network_used`, `memory_read`, `memory_written`, `tokens_consumed`, `cost_consumed`, `runtime_enabled`, `executed`) permanece `false`; `simulation=true`, `production_blocked=true`, `rollout_percentage=0`. **Esta PR não cria um Execution Gateway, não cria um runtime, e não executa nada real.**

## ValidationState

`validation-state.js` define o enum de 4 estados que substitui as flags binárias: `NOT_EVALUATED` (padrão), `VALID`, `INVALID`, `NOT_APPLICABLE`. `ALLOWED_TRANSITIONS` permite apenas `NOT_EVALUATED → {VALID, INVALID, NOT_APPLICABLE}` — nunca uma transição entre dois estados já resolvidos. **Cada flag deve representar exatamente o que foi avaliado, nunca o que se presume.** Uma etapa nunca alcançada (porque a avaliação parou em um bloqueador anterior) é `NOT_EVALUATED`, nunca `VALID` por omissão nem `INVALID` por suposição.

## ValidationOutcome

`validation-outcome.js` (17 campos exatos: `validator_id`, `validator_version`, `validation_stage`, `state`, `status`, `severity`, `reason_codes`, `evidence_reference_ids`, `input_fingerprint`, `output_fingerprint`, `evaluated`, `applicable`, `blocking`, `terminal`, `logical_sequence`, `simulation`, `production_blocked`) registra o resultado de um único validador para uma única etapa. `VALIDATION_STAGES` formaliza, como enum único, a ordem de 22 etapas que o próprio `execution-plan-engine.js` já seguia implicitamente desde as PRs #94-#100: `SCHEMA, SIMULATION_CONTEXT, IDENTITY, TENANT, ORGANIZATION, PROJECT, SESSION, TASK, AUTHORIZATION, AUTHORIZATION_PROVENANCE, AUTHORIZATION_SCOPE, REGISTRY_SNAPSHOT, EVIDENCE, STAGE_MANIFEST, DEPENDENCY_GRAPH, REFERENCE_BINDING, BUDGET, IDEMPOTENCY, STOP_CONDITIONS, COMPENSATIONS, PACKAGE_INTEGRITY, FINALIZATION`.

`evaluated`/`applicable` são estritamente derivados de `state`, nunca aceitos independentemente do chamador — o mesmo rigor de boolean derivado que `execution_plan_prepared`/`snapshot_consistent` já estabeleceram em PRs anteriores. `blocking` só pode ser `true` quando `state === 'INVALID'`; `terminal` só pode ser `true` quando `blocking === true`. Para `VALID`/`NOT_APPLICABLE`/`NOT_EVALUATED`, `status` usa um sentinel determinístico `` `${stage}_${state}` `` (ex. `'TENANT_VALID'`) quando o chamador não fornece um; para `INVALID`, `status` é sempre um dos 24 status oficiais da taxonomia.

## ValidationLedger

`validation-ledger.js` (29 campos exatos) consolida uma sequência de `ValidationOutcome`s em um único registro auditável. `execution_plan_request_id`/`execution_plan_id` são deliberadamente nullable — **um único contrato serve tanto `execution-plan-engine.js` (ambos preenchidos) quanto `execution-authorization-boundary.js` (ambos nulos, já que uma requisição de autorização ainda não tem um plano de execução seu)**, evitando duplicar o contrato ("Pode usar ValidationLedger próprio da autorização ou adaptar ao ledger comum com execution_plan_id nullable").

Todos os 8 contadores (`evaluated_count`, `valid_count`, `invalid_count`, `not_applicable_count`, `not_evaluated_count`, `blocking_count`, `terminal_count`, `validation_outcome_count`) são derivados de `validation_outcomes` e cross-checados pelo validador — nunca declarados independentemente. `validation_outcome_ids` segue o formato `` `${stage}::${validator_id}` ``, deve ser único, e os outcomes devem estar ordenados por `logical_sequence`. **Uma vez que existe um bloqueador, toda etapa lógica posterior permanece `NOT_EVALUATED`** — o validador rejeita qualquer outcome posterior ao primeiro bloqueador que não seja `NOT_EVALUATED`. `pipeline_completed = (not_evaluated_count === 0)`; `all_required_validations_valid = (invalid_count === 0 && not_evaluated_count === 0)`; nenhum bloqueador pode coexistir com `all_required_validations_valid = true`.

## ValidationTaxonomy

`validation-taxonomy.js` formaliza os 24 status oficiais em `TAXONOMY_STATUSES`, cada um com metadados (`stage`, `severity`, `blocking`) em `TAXONOMY_METADATA`. `PRECEDENCE_ORDER` é uma ordenação separada e intencionalmente distinta da ordem de declaração, refletindo a ordem real em que o engine avalia cada bloqueador (alguns status como `FINGERPRINT_BLOCKED`/`VERSION_BLOCKED`/`CONFLICT_BLOCKED` são transversais a múltiplas etapas). `LEGACY_STATUS_ALIASES` está deliberadamente vazio — **é honesto: nenhuma renomeação de status realmente aconteceu ainda**, o mecanismo existe pronto para quando uma acontecer.

## ValidationStatusMapper

`validation-status-mapper.js` conecta a taxonomia única às duas vocabulárias externas que a antecedem: `EXECUTION_PLAN_STATUSES` e `RESULT_STATUSES`. `CONTRACT_STATUS_OVERRIDES`/`RESULT_STATUS_OVERRIDES` estão ambos vazios — após a correção do enum (`EXECUTION_PLAN_PREPARED_SIMULATION`/`BINDING_BLOCKED` agora presentes), o status da taxonomia é mapeado por identidade para ambos os alvos. Um status não reconhecido cai para `UNKNOWN_STATUS_BLOCKED` quando o enum-alvo o possui (como `AUTHORIZATION_STATUSES`), ou para `VALIDATION_FAILED` fail-closed caso contrário. `MEMORY_BLOCKED`/`CONTEXT_BLOCKED`/`MODEL_BLOCKED`/`TOOL_BLOCKED`/`WORKFLOW_BLOCKED` permanecem uma assimetria intencional e documentada desde a PR #96-100 (o contrato mantém o status específico, o resultado colapsa para `VALIDATION_FAILED`) — fora do escopo desta taxonomia de 24 status, deliberadamente não tocada.

## ValidationRegistry e ValidationPipeline

`validation-registry.js` constrói um registro de validadores estático e explícito — **nunca descoberta dinâmica via `import()`**. Cada definição exige `validator_id`, `version`, `stage` (um de `VALIDATION_STAGES`), `priority`, `required` (boolean), `applicable` (predicado síncrono), `handler` (função pura síncrona — `AsyncFunction`/`GeneratorFunction` são rejeitadas na construção). A ordenação é determinística: ordem canônica de `VALIDATION_STAGES`, depois `priority`, depois `validator_id` como desempate — nunca ordem de registro.

`validation-pipeline.js` fornece dois caminhos:

- **`runValidationPipeline`**: uma pipeline forward real que percorre `VALIDATION_STAGES`, invoca cada validador registrado via `adaptLegacyValidatorOutput`/`invokeValidatorHandler` (que normalizam as três formas legadas de retorno deste codebase — `{valid, errors}`, `null`/`{status, reason}`, e uma exceção — sem reescrever nenhum validador existente), e para na primeira falha obrigatória, marcando todo o restante `NOT_EVALUATED`. `execution-plan-validation-registry.js` (22 validadores, um por etapa canônica) é uma instância real e independentemente testável deste registro, reutilizando diretamente os validadores puros já existentes (`validateExecutionPlanRequest`, `validateAgentSimulationContext`, `validateOrchestratorStageManifestReference`, `validateExecutionPlanDependencyGraphReference`) onde aplicável.
- **`deriveValidationLedgerFromStatus`**: dado o `status` final que `execution-plan-engine.js` já computou (e a posição desse status na taxonomia), deriva o `ValidationLedger` que uma execução forward completa da pipeline teria produzido — toda etapa estritamente anterior à etapa bloqueadora é `VALID`, a etapa bloqueadora é `INVALID`, e toda etapa posterior é `NOT_EVALUATED`. Ver "Limitações" para por que esta é a integração real com o engine, em vez de `runValidationPipeline`.

## Integração com Execution Plan Engine

`execution-plan-engine.js`'s `buildOutcome()` agora computa um `ValidationLedger` via `deriveValidationLedgerFromStatus` a partir do `status` que a longa cadeia sequencial de gates já determinou, e usa esse ledger para popular `validation_ledger_id`/`validation_ledger_fingerprint`/`validation_pipeline_completed`/`architecture_gates_passed` (4 novos campos em `ExecutionPlanContract`, agora 65) e os 7 novos campos equivalentes em `ExecutionPlanResult` (agora 92, incluindo `first_blocking_stage`/`first_blocking_status`, nullable em par). **Todo flag `*_validated` que antes era hardcoded `true` agora é derivado honestamente de `isStageValid(ledger, STAGE)`**: `authorization_validated = outcome(AUTHORIZATION).state === VALID`, `evidence_validated = outcome(EVIDENCE)`, `bindings_validated = outcome(REFERENCE_BINDING)`, `budget_validated = outcome(BUDGET)`, `dependencies_validated = outcome(DEPENDENCY_GRAPH)`, `idempotency_validated = outcome(IDEMPOTENCY)`, `stop_conditions_validated = outcome(STOP_CONDITIONS)`, `compensations_validated = outcome(COMPENSATIONS)`.

`EXECUTION_PLAN_STATUSES` ganha `'EXECUTION_PLAN_PREPARED_SIMULATION'`/`'BINDING_BLOCKED'` (31 status agora, +2) — o defeito "Status colapsados" que esta PR existe para corrigir. `'PREPARED_SIMULATION'` permanece no enum como entrada legada inerte, nunca mais produzida por este mapper; `PREPARED_STATUS_ALIASES` cobre ambos os literais para o cálculo de `execution_plan_prepared`.

## Integração com Authorization Boundary

`execution-authorization-boundary.js` tinha o mesmo defeito: `buildDecisionForRequest()`, chamada de todo ponto de retorno antecipado (bloqueado ou não), retornava `orchestrator_decision_validated`/`evidence_bundle_validated`/`bindings_validated`/`fingerprints_validated`/`actor_validated`/`role_validated`/`scope_validated`/`risk_validated`/`approval_validated`/`budget_validated`/`expiration_validated` hardcoded `true` independentemente de qual etapa bloqueou. Corrigido com um `AUTHORIZATION_VALIDATION_STAGE_ORDER` explícito e cada um dos 27 pontos de chamada em `evaluateExecutionAuthorizationRequest` agora se identifica com a etapa real que alcançou (`'REQUEST'` para o próprio contrato da requisição, o nome do flag para cada bloqueio específico, `'SUCCESS'` para `AUTHORIZED_SIMULATION`/`DENY`) — nunca reconstruído heuristicamente a partir do `status` sozinho, já que vários status (`TENANT_BLOCKED`, `BUDGET_BLOCKED`, `APPROVAL_BLOCKED`, ...) são alcançáveis tanto por tradução antecipada da decisão do Orchestrator quanto pelo próprio check nativo tardio deste módulo, e só o ponto de chamada sabe honestamente qual dos dois realmente aconteceu. `versions_validated` permanece hardcoded `true` — a verificação de versão que este flag refletia foi removida por completo (ver abaixo); vacuamente verdadeiro, sem check vivo que possa torná-lo falso.

`ValidationLedger` serve este módulo com `execution_plan_request_id`/`execution_plan_id` ambos nulos, o mesmo contrato compartilhado descrito acima.

## Nenhuma condição decisória é lida de context

`context.currentRegistryVersion` era o último side-channel decisório restante em três módulos: `execution-plan-engine.js` (já removido na PR #100), `execution-authorization-boundary.js`, e `orchestrator-decision-engine.js` — ambos removidos nesta PR. Um `expected_registry_version` obsoleto passado via `context` agora não tem efeito algum (dead side-channel), confirmado por teste dedicado em ambos os módulos. `memory-selection-engine.js` mantém uma leitura análoga, genuína, pré-existente — fora da lista de arquivos a modificar desta PR, documentada honestamente como débito técnico conhecido em vez de silenciosamente ignorada (ver "Limitações").

## Architecture Gates

`architecture-gate-rules.js`/`architecture-gate-runner.js` definem 21 gates, divididos em duas categorias porque uma varredura textual ingênua de todo o diretório provou-se frágil demais contra 280+ arquivos pré-existentes de convenções variadas (25 falsos positivos na primeira tentativa, documentados abaixo em "Limitações"):

- **12 gates de padrão** (`FORBIDDEN_NETWORK_IMPORT`, `FORBIDDEN_FILESYSTEM_WRITE`, `FORBIDDEN_CHILD_PROCESS`, `FORBIDDEN_EVAL`, `FORBIDDEN_DYNAMIC_IMPORT`, `FORBIDDEN_RUNTIME_IMPORT`, `FORBIDDEN_PROVIDER_SDK`, `FORBIDDEN_PROCESS_ENV_OPERATIONAL`, `FORBIDDEN_TIMER`, `FORBIDDEN_MUTABLE_GLOBAL`, `FORBIDDEN_ENDPOINT_IN_CORE`, `NO_SIDE_CHANNEL_CONTEXT`) varrem `src/core/*.js` linha a linha (ignorando linhas de comentário), com um allowlist mínimo por arquivo para exceções verificadas (ex. `canonical-content-digest.js` e três arquivos `public-web-*` pré-existentes usam apenas `crypto.createHash('sha256')`, nunca HMAC/segredo/rede).
- **9 gates estruturais** (`SIMULATION_FLAG_REQUIRED`, `PRODUCTION_BLOCKED_REQUIRED`, `ROLLOUT_ZERO_REQUIRED`, `TEST_REGISTRATION_REQUIRED`, `VALIDATOR_REGISTRATION_REQUIRED`, `STATUS_TAXONOMY_REQUIRED`, `FINGERPRINT_COVERAGE_REQUIRED`, `VERSION_COVERAGE_REQUIRED`, `EXACT_FIELDS_REQUIRED`) checam um `AUDITED_CONTRACTS_MANIFEST` explícito e curado (~19 módulos da linhagem PR #94-#101) via introspecção estrutural real — requerendo cada módulo e inspecionando seus exports reais de `FIELDS`/`SAFE_FLAGS` — em vez de heurística de texto. **"Usar manifesto explícito de contratos auditados para evitar heurística frágil"** — a própria instrução da especificação para o gate de cobertura de fingerprint/versão, generalizada aqui para os 9 gates estruturais pela mesma razão: arquivos pré-existentes das PRs #85-#93 usam vários idiomas igualmente válidos mas diferentes para forçar `simulation=true`, e nenhum regex único reconhece todos com segurança.

`scripts/run-architecture-gates.js` roda todos os 21 gates e reporta `[GATE_ID] arquivo:linha -- descrição` para cada achado, saindo com código 1 se houver algum. **Hoje: 0 achados.**

## Test Discovery

`scripts/discover-tests.js` substitui a lista de 77 arquivos mantida manualmente em `package.json`'s `test` script por descoberta determinística via `fs.readdirSync` + filtro `.endsWith('.test.js')` + ordenação — sem dependência de glob, portável entre Windows e Linux. `--audit` compara os arquivos descobertos contra o que o script `test` do `package.json` de fato executa, reportando qualquer arquivo descoberto mas não registrado. **Isto detectou um bug real e pré-existente antes desta correção**: `test/execution-reference-binding-provenance.test.js` (87 testes, da PR #100) nunca havia rodado sob `npm test`, apenas sob invocação direta `node --test <arquivo>` — a exata classe de defeito que este requisito da PR existe para prevenir, e uma validação concreta de toda a premissa desta PR. `package.json`'s `test` script agora delega inteiramente a este script; `test:audit` e `gates` são scripts npm dedicados para os dois mecanismos.

## Confirmação de nenhuma execução real

Todo novo contrato força `simulation=true`/`production_blocked=true`. `architecture-gate-runner.js` é o único módulo com permissão para acesso a filesystem fora de scripts/testes (`fs.readdirSync`/`require` para introspecção — nunca escrita). `validation-pipeline.js`'s `invokeValidatorHandler` nunca deixa uma exceção escapar sem sanitização, e o texto bruto de uma exceção nunca vaza para o resultado adaptado. **Nenhum agente, modelo, provider, ferramenta ou workflow é executado nesta implementação.**

## Limitações

- **`deriveValidationLedgerFromStatus` (post-hoc), não `runValidationPipeline` (forward), é o que `execution-plan-engine.js` realmente usa.** Reescrever a cadeia sequencial de ~700 linhas do engine, já testada, em validadores de pipeline individualmente registrados foi julgado grande e arriscado demais para fazer ao mesmo tempo em que se introduzia semântica de validação progressiva. Em vez disso, `deriveValidationLedgerFromStatus` deriva o `ValidationLedger` que uma execução forward real teria produzido, diretamente do `status` que o engine já computou e da ordenação canônica de etapas da taxonomia — produzindo a mesma forma observável de ledger, sem reexecutar (e arriscar divergir de) a lógica de decisão já correta do engine. Uma pipeline forward genuína e independentemente testável (`runValidationPipeline` + `execution-plan-validation-registry.js`, 22 validadores reais) existe e funciona por conta própria, satisfazendo o requisito de "registry e pipeline reais" mesmo não sendo o caminho que o engine efetivamente invoca.
- **A varredura de padrões dos 12 gates textuais cobre apenas `src/core/*.js`**, nunca `test/`, deliberadamente — arquivos de teste legitimamente referenciam os mesmos padrões proibidos como dados de fixture literais para testar o próprio detector.
- **`memory-selection-engine.js` mantém seu próprio `context.currentRegistryVersion`**, um side-channel genuíno e pré-existente, fora da lista de arquivos a modificar desta PR — alistado honestamente como débito técnico conhecido em `architecture-gate-rules.js`'s `ALLOWLIST`, nunca silenciosamente ignorado.
- **Falsos positivos da primeira tentativa da varredura ingênua** (25 achados em 21 arquivos) incluíam: o próprio arquivo de regras se auto-detectando pelas strings de descrição de suas regras (corrigido reescrevendo as descrições); `let`/`var` de escopo de função sendo confundidos com globais mutáveis de módulo (corrigido exigindo coluna 0); o padrão comum `env = process.env` de injeção de dependência sendo confundido com leitura operacional direta (corrigido estreitando o regex); comentários históricos mencionando o side-channel já removido sendo confundidos com o código real (corrigido pulando linhas de comentário).
- **`versions_validated` em `ExecutionAuthorizationDecision` é vacuamente `true`** — a verificação que este flag refletia foi removida por completo junto com o side-channel `context.currentRegistryVersion`; não há checagem viva que possa torná-lo `false`. `VERSION_BLOCKED` permanece no enum `AUTHORIZATION_STATUSES`/`RESULT_STATUSES` apenas como entrada legada, atualmente inalcançável.

**A próxima etapa arquitetural continua sendo definida por decisão explícita futura, não pela criação de um Execution Gateway ou runtime nesta PR.**
