# Hermes Agent Core - Execution Gateway Boundary Simulation

## Objetivo

As PRs #94-#101 produzem, sucessivamente, um `ExecutionPlanContract`/`ExecutionPlanResult` totalmente preparado e validado (`EXECUTION_PLAN_PREPARED_SIMULATION`), um `ExecutionAuthorizationDecision` autorizado (`AUTHORIZED_SIMULATION`), referências de binding/provenance/scope/snapshot vinculadas, e um `ValidationLedger` honesto e progressivo — mas nenhum desses módulos decide, sozinho, se esse pacote pronto pode ser **aceito para simulação**. Esta PR cria o **Execution Gateway Boundary** — a última fronteira declarativa antes de uma futura Runtime Execution Simulation — que recebe um pacote já pronto e decide apenas `GATEWAY_ACCEPTED_SIMULATION` ou um dos 27 status de bloqueio, sem nunca executar, despachar, iniciar um stage, chamar um agente/model/provider/tool/workflow, carregar memória, abrir rede, ou criar job/queue/worker.

**VALIDATED ≠ READY ≠ AUTHORIZED ≠ ACCEPTED ≠ EXECUTABLE ≠ EXECUTION_STARTED ≠ EXECUTED.** Mesmo no melhor cenário desta PR — `status='GATEWAY_ACCEPTED_SIMULATION'`, `gateway_accepted_in_simulation=true` — todos os 21 flags operacionais (`runtime_enabled`, `execution_authorized`, `execution_started`, `stage_started`, `stage_completed`, `agent_executed`, `tool_called`, `workflow_executed`, `provider_called`, `model_called`, `network_used`, `memory_read`, `memory_written`, `tokens_consumed`, `cost_consumed`, `job_created`, `queue_used`, `worker_started`, `executed`) permanecem `false`; `simulation=true`, `production_blocked=true`, `rollout_percentage=0`. **Esta PR não cria um runtime e não executa nada real.**

### Correção pós-auditoria (pr102fix)

Uma auditoria via MCP do GitHub aprovou a arquitetura geral, package integrity, architecture evidence, ledgers, freshness, replay, CI e segurança de simulação, mas encontrou dois defeitos obrigatórios de corrigir:

1. **Classificação de pacote NO_LLM incorreta.** A implementação original classificava um pacote como NO_LLM apenas quando `stageTypes.size === 0` — mas um plano NO_LLM ou determinístico legitimamente continua contendo `VALIDATION_STAGE`/`DETERMINISTIC_STAGE`/`AUDIT_STAGE`/`FINALIZATION_STAGE`/etc., então essa condição nunca era verdadeira para um pacote real, deixando `allow_no_llm_package` silenciosamente nunca aplicado. **NO_LLM é definido pela ausência de `MODEL_REFERENCE_STAGE` e de model bindings, não pela ausência de estágios.** Corrigido: `isNoLlmPackage = !hasModelStage && !hasStageModelReference`, onde `hasModelStage` verifica a presença do tipo de stage e `hasStageModelReference` verifica se qualquer stage record carrega um `model_selection_reference_id` não-nulo. Um pacote de tool/workflow sem stage de modelo continua sendo classificado NO_LLM (e precisa respeitar `allow_no_llm_package` **e** `allow_tool_reference_package`/`allow_workflow_reference_package` independentemente) — os dois checks nunca são mutuamente exclusivos. Consistência fail-closed adicionada: um `MODEL_REFERENCE_STAGE` sem `model_selection_reference_id`, ou um `model_selection_reference_id` fora de um `MODEL_REFERENCE_STAGE`, bloqueia `POLICY_BLOCKED` antes mesmo da classificação rodar — um pacote internamente inconsistente nunca é silenciosamente reclassificado em nenhuma direção. Nenhum modelo é selecionado ou alterado por esta checagem.
2. **`policy_validated` marcado prematuramente.** A implementação original marcava `policy_validated=true` logo após a validação estrutural do request, antes de qualquer um dos checks semânticos (`allow_no_llm_package`/`allow_model_reference_package`/`allow_tool_reference_package`/`allow_workflow_reference_package`/`allow_parallel_package`) rodar — um resultado `POLICY_BLOCKED` podia sair com `policy_validated=true`. **`policy_validated` significa que tanto o contrato quanto todas as regras semânticas aplicáveis foram avaliados com sucesso.** Corrigido: `markValid('policy_validated')` foi movido para depois de todo o bloco de checks policy-driven (NO_LLM, model, tool, workflow, parallel), de modo que qualquer `return finalize('POLICY_BLOCKED', ...)` anterior a ele deixa `policy_validated=false` no `validatedFlags` — a mesma disciplina "nunca marcar válido antes de genuinamente confirmar" já estabelecida por `markValid`/`markValidationValid` em toda a linhagem desta PR. `allow_waiting_approval_package`/`allow_external_side_effect_reference`/`allow_irreversible_reference` continuam vacuamente satisfeitos (nenhum sinal correspondente de "requer aprovação em espera / efeito colateral externo / ação irreversível" existe em nenhum lugar do pacote para comparar contra eles) — a mesma categoria honesta que os flags `require_*`/`fail_on_*`, cujas invariantes subjacentes já são impostas incondicionalmente pelos passos anteriores do pipeline que eles nomeiam, nunca por um check próprio aqui.

## Novos contratos

### ArchitectureGateEvidenceReference

`architecture-gate-evidence-reference.js` (28 campos exatos) é a evidência declarativa, vinculada a um commit SHA e a um workflow run específicos, de que os 21 architecture gates da PR #101 passaram para aquele commit — a lacuna que a própria PR #101 documentou honestamente em sua seção "Limitações" (`architecture_gates_passed` sempre `false` por falta desta evidência). `deriveEvidenceStatus()` computa `evidence_status` (6 valores: `ARCHITECTURE_GATES_PASSED_SIMULATION`, `_FAILED`, `_INCOMPLETE`, `_EXPIRED_LOGICAL`, `_CONFLICTED`, `_VALIDATION_FAILED`) via uma cadeia ordenada de checagens — expirado lógico primeiro, depois workflow run incompleto, depois conclusão ≠ `SUCCESS`, depois `head_commit_sha` do workflow run divergindo do `commit_sha` declarado (`CONFLICTED`), depois qualquer gate obrigatório falho. **Nunca consulta o GitHub real** — apenas valida a evidência declarativa que o próprio `request` já carrega.

### ExecutionGatewayPolicy

`execution-gateway-policy.js` (37 campos exatos: 9 `allow_*`, 17 `require_*`, 6 `fail_on_*`, mais `simulation`/`production_blocked`/ids/versão) é quase inteiramente `SAFE_FLAGS` forçados — apenas 6 campos são genuinamente configuráveis pelo chamador: `allow_no_llm_package`, `allow_model_reference_package`, `allow_tool_reference_package`, `allow_workflow_reference_package`, `allow_parallel_package`, `fail_on_warning`. Todo `require_*` é forçado `true`; `allow_waiting_approval_package`/`allow_external_side_effect_reference`/`allow_irreversible_reference` são forçados `false`.

### ExecutionGatewayFreshnessReference

`execution-gateway-freshness-reference.js` (19 campos exatos) avalia frescor puramente por números de sequência lógica que o chamador já carrega — **nunca `Date.now()`, nunca `new Date()`, nunca timer**. `package_expired_logically` é sempre derivado: `(current_logical_sequence - created_logical_sequence) > maximum_valid_sequences`. `freshness_validated = !(qualquer um dos 4 flags de expiração === true)`.

### ExecutionGatewayReplayReference

`execution-gateway-replay-reference.js` (20 campos exatos) protege contra replay/duplicação sem nunca iniciar uma tentativa real. O builder **lança exceção** (não seta um flag) se `expected_gateway_attempt > maximum_gateway_attempts` — uma regra estrutural, não uma flag suave, o que torna `replay_allowed=false` inalcançável via construção bem-formada (ver "Limitações"). `prior_gateway_decision_ids`/`prior_gateway_decision_fingerprints` são dois arrays paralelos: são canonicalizados **como pares** `(id, fingerprint)` — nunca ordenados independentemente, o que corromperia silenciosamente a correspondência 1:1 entre os dois arrays (bug real encontrado e corrigido durante o desenvolvimento desta PR; ver commit).

### ExecutionGatewayPackageReference

`execution-gateway-package-reference.js` (42 campos exatos: 12 ids, 11 fingerprints) é um resumo compacto e autocontido do pacote inteiro — nenhum conteúdo dos objetos referenciados é embutido, apenas ids e fingerprints. `package_reference_validated` é derivado de completude estrutural (todo id/fingerprint presente e não-vazio, mais `execution_plan_status`/`execution_plan_result_status` batendo com os literais exigidos) — mas como esses mesmos dois status já são exigidos incondicionalmente pelo próprio validador do contrato, o builder nunca consegue produzir `package_reference_validated=false` para um objeto que ele mesmo aceitou construir (outra instância de "segurança por construção"; ver "Limitações"). **A checagem cruzada real contra os objetos de fato referenciados é trabalho do Gateway Boundary, nunca deste contrato sozinho.**

### ExecutionGatewayRequest

`execution-gateway-request.js` (24 campos exatos) agrega as 15 referências aninhadas do Gateway (`gateway_policy`, `gateway_package_reference`, `execution_plan_reference`, `execution_plan_result_reference`, `authorization_decision_reference`, `authorization_provenance_reference`, `authorization_scope_reference`, `registry_snapshot_reference`, `stage_manifest_reference`, `dependency_graph_reference`, `binding_ledger_reference`, `validation_ledger_reference`, `architecture_gate_evidence_reference`, `freshness_reference`, `replay_reference`) e valida cada uma contra seu **validador real já existente** (`NESTED_REFERENCE_VALIDATORS`) — nunca uma reimplementação paralela mais fraca. `authorization_decision_reference` é o `ExecutionAuthorizationDecision` completo (70 campos), não o `AuthorizationDecisionReference` menor já embutido no plano — são contratos genuinamente diferentes.

### ExecutionGatewayDecision / ExecutionGatewayResult / ExecutionGatewayAudit

`execution-gateway-decision.js` define uma taxonomia própria e autocontida de 29 status (`GATEWAY_STATUSES`), sua ordem real de precedência (`GATEWAY_PRECEDENCE_ORDER`, idêntica à ordem de declaração desta vez pois a especificação forneceu uma lista numerada explícita), 10 decisões e 10 próximos estados, e um `STATUS_OUTCOME_MAP` que fixa `decision`/`next_state` por status — nunca reconstruído heuristicamente. **Não reutiliza `validation-outcome.js`'s `VALIDATION_STAGES`** (fora da lista de arquivos a modificar desta PR) nem cria uma extensão do enum de 22 stages já existente — usa sua própria taxonomia de 29 status, exatamente a permissão que a especificação concede ("Stages específicos do Gateway podem usar uma taxonomy própria ou extensão documentada"). `execution-gateway-result.js` é um envelope fino sobre a decisão, sempre copiando `status`/`decision`/`next_state`, nunca uma fonte independente de verdade. `execution-gateway-audit.js` nunca registra payload/conteúdo/prompt/segredo — apenas ids, fingerprints, digest, status/decision/next_state, bindings de tenant/organization/project/session/agent/actor, e 3 conjuntos de contadores (gates, validações, bindings).

### ExecutionGatewayBoundary

`execution-gateway-boundary.js`'s `evaluateExecutionGatewayRequest(request, context = {})` é o avaliador central — 28 passos sequenciais, cada um recomputando ou comparando algo real (um id, um fingerprint recomputado, um digest recomputado) em vez de confiar em uma flag isolada que o chamador poderia ter construído à mão ("Gateway não pode confiar apenas em flags"). `context` nunca é lido para nenhuma decisão, mantendo a mesma disciplina "nenhum side-channel" de todo engine desde a PR #98fix. A ordem real: request válido → plano preparado → resultado preparado → package reference íntegra → identidade (tenant/organization/project/session/agent/actor) → autorização → provenance → scope → registry snapshot → stage manifest → dependency graph → binding ledger → validation ledger → architecture gate evidence → fingerprints do pacote → digest do pacote → freshness → replay → política (tipos de stage permitidos) → invariantes de não-execução agregados → `GATEWAY_ACCEPTED_SIMULATION`.

`execution-gateway-registry.js` segue a mesma disciplina `createEntityStore`/`resolveRegistration` (replay → payload mismatch → conflito de versão → conflito de fingerprint → downgrade de versão → aceito) já estabelecida por todo registro deste codebase, duplicada localmente por convenção (nenhum módulo compartilhado de registry existe hoje).

## Correção de compounding de fingerprint

O mesmo defeito que a PR #100 já havia corrigido uma vez (embutir um fingerprint canônico já grande como um valor de campo simples dentro de um objeto que também será fingerprintado depois, comprimindo exponencialmente através de camadas) reapareceu nesta PR numa camada nova: `plan.plan_fingerprint`/`result.execution_plan_fingerprint` (cada um ~100KB, característica pré-existente das PRs #99-#101) são copiados como campos simples em `ExecutionGatewayPackageReference` e em `ExecutionGatewayReplayReference`; o próprio `ExecutionGatewayRequest` embute o pacote inteiro; a `ExecutionGatewayDecision` embute o fingerprint do request; o `ExecutionGatewayResult` embute o fingerprint da decisão. Sem correção, um único cenário de fixture chegava a **17.5MB**, e `replay_fingerprint` sozinho chegava a **180KB** (autoincluindo `execution_plan_fingerprint`, uma cópia de 127KB).

Corrigido com o mesmo remédio já estabelecido pela PR #100: `computeCanonicalContentDigest()` (digest SHA-256 fixo de ~71 caracteres) em vez do `stablePayload` bruto, aplicado a exatamente 4 campos: `requestFingerprint`/`gatewayPackageFingerprint` (calculados em `execution-gateway-boundary.js`), `gateway_decision_fingerprint` (calculado em `buildOutcome()`), e `replay_fingerprint` (calculado em `execution-gateway-replay-reference.js`'s próprio `computeReplayFingerprint`). Um único cenário caiu de 17.5MB para ~1.4MB (request + decision). Os campos que precisam permanecer como cópia byte-a-byte do fingerprint real do objeto que descrevem (`packageRef.execution_plan_fingerprint`, `packageRef.execution_plan_result_fingerprint` — comparados por igualdade exata contra `plan.plan_fingerprint`/`result.execution_plan_fingerprint` no passo 22 do boundary) permanecem intocados: usar um digest ali quebraria a semântica da própria checagem cruzada.

## Fixture

`test/fixtures/hermes-execution-gateway-boundary-simulation.json` (~27MB, em linha com o precedente de `hermes-execution-plan-contracts.json` em 23.8MB e `hermes-execution-reference-binding-provenance.json` em 21.8MB) contém **19 cenários curados** — um representante por camada de bloqueio do boundary, mais os 4 caminhos aceitos (sem LLM, model reference, tool reference, workflow reference) — armazenando apenas `{request, decision}` por cenário, não `{request, decision, result, audit}`. A cauda longa de mutações de um único campo (mismatches de organization/project/session/agent/actor além do tenant já coberto na fixture, variantes de evidência arquitetural, variantes de freshness, replay por duplicação, ordem canônica de campos, side-channel de contexto) é coberta **inline** em `test/execution-gateway-boundary-simulation.test.js`, construída via `test/helpers/execution-gateway-test-data.js` (o mesmo "golden bundle" que gerou a fixture, promovido a helper permanente de teste) — nunca persistida como mais um cenário JSON de ~1.4MB. Isso evita reproduzir, para 43+ cenários quase idênticos, o mesmo custo de armazenamento que só se justifica quando o cenário exercita um caminho de código genuinamente distinto.

## Confirmação de nenhuma execução real

Todo novo contrato força `simulation=true`/`production_blocked=true`. Nenhum flag operacional pode ser `true` em nenhuma referência aninhada bem-formada (todos são `SAFE_FLAGS` forçados nos próprios builders de PRs anteriores) — o passo final do boundary (`non_execution_invariants_validated`) é uma checagem agregada redundante e deliberada sobre isso, não a única linha de defesa. `context` nunca é lido para nenhuma decisão (teste dedicado injeta um `context` hostil com `execution_authorized: true`/`network_used: true`/etc. e confirma zero efeito). **Nenhum agente, modelo, provider, ferramenta ou workflow é executado nesta implementação.**

## Limitações

- **`replay_allowed=false`/`operational-flag-override` são inalcançáveis via construção bem-formada.** `ExecutionGatewayReplayReference`'s builder lança exceção (não seta uma flag) quando `expected_gateway_attempt > maximum_gateway_attempts`; todo flag operacional em toda referência aninhada é um `SAFE_FLAGS` forçado no builder de origem. A única checagem de replay genuinamente alcançável no boundary é o mismatch de `execution_plan_fingerprint` entre a referência de replay e o plano real que ela descreve (passo 25) — coberta pela fixture (`replay-blocked`).
- **`package_reference_validated` nunca pode ser `false` para um objeto que `buildExecutionGatewayPackageReference` de fato construiu**, pelo mesmo motivo: `execution_plan_status`/`execution_plan_result_status` divergentes do literal exigido já são um erro de validação incondicional, não apenas um componente do cálculo de `structurallyComplete`. O teste correspondente valida a lógica agregada do validador diretamente (um objeto adulterado à mão com `package_reference_validated=true` mas status divergente), não via o builder.
- **`expected_gateway_registry_version` é validado estruturalmente (inteiro ≥ 1) mas nunca comparado contra nada real.** O boundary é um avaliador puro e sem estado — não existe, hoje, um "oráculo" de versão de registry ao vivo para comparar contra ele dentro desta função; essa comparação pertenceria a uma camada com estado (o próprio `execution-gateway-registry.js`, ou um chamador que mantenha o registry real), não a este avaliador declarativo. Documentado explicitamente, não corrigido silenciosamente como se fosse um bug.
- **`prior_gateway_decision_ids`/`prior_gateway_decision_fingerprints` não são cross-checados contra nenhum histórico real dentro do boundary.** `duplicate_gateway_acceptance_blocked` é um `SAFE_FLAGS` sempre `true` (nunca uma checagem viva) — a detecção real de duplicata pertenceria ao registry com estado (`registerExecutionGatewayDecision`'s própria lógica de replay/payload-mismatch, já testada), não a este avaliador stateless que nunca vê decisões anteriores.
- **O digest do pacote (`package_digest`) cobre exatamente 11 objetos** (`plan`, `result`, `authorizationDecision`, `provenanceReference`, `scopeReference`, `snapshotReference`, `stageManifestReference`, `dependencyGraphReference`, `bindingLedger`, `validationLedger`, `evidenceReference`) — a mesma forma exata usada tanto na construção (fixture builder / qualquer chamador futuro) quanto na recomputação do boundary; qualquer chamador que construa esse digest com um subconjunto diferente de campos produzirá um digest que nunca vai bater, por design.
- **`plan.plan_fingerprint`/`result.execution_plan_fingerprint` continuam ~100KB cada**, característica pré-existente das PRs #99-#101, fora do escopo desta PR corrigir retroativamente — é exatamente por isso que os 4 pontos de correção desta PR (ver "Correção de compounding de fingerprint") usam digest em vez de tentar reduzir esses dois campos na origem.

Nenhum campo ou comportamento deste contrato foi alterado.)*
