# Hermes Agent Core - Execution Plan Stage Manifest Integrity

## Objetivo

This PR fixes an integrity and provenance defect found after PR #98: `execution-plan-engine.js` used to *derive* each stage's `stage_type` from which plan-level references were present (a model selection present → `MODEL_REFERENCE_STAGE`, tools present → `TOOL_REFERENCE_STAGE`, otherwise `DETERMINISTIC_STAGE`), and forced `parallelizable=false`, `optional=false`, and every estimate to `0` on every stage regardless of what the Agent Orchestrator Planner had actually declared. Several stages the Planner classified differently (`VALIDATION_STAGE`, `MEMORY_REFERENCE_STAGE`, `CONTEXT_REFERENCE_STAGE`, `AUDIT_STAGE`, `FINALIZATION_STAGE`) could all collapse into the same reconstructed `MODEL_REFERENCE_STAGE`, and every stage's real token/cost estimate was silently zeroed.

**O Execution Plan não reconstrói a semântica dos estágios. Ele preserva os StageRecords produzidos pelo Planner.**

This PR introduces `OrchestratorStageManifestReference` — a versioned, fingerprinted, tenant/organization/project/session/agent-bound manifest that becomes the sole source of stage semantics — and removes `deriveStageType` and every estimate-zeroing default from the engine entirely.

## Preservação 1:1 dos estágios

`execution-plan-engine.js` now materializes each `ExecutionPlanStage` directly from its corresponding `StageRecord`, field for field: `stage_type`, `stage_sequence`, `agent_reference_id`, `task_reference_id`, `model_selection_reference_id`, `context_assembly_reference_id`, `memory_selection_reference_id`, `tool_reference_ids`, `workflow_reference_id`, `dependency_ids` (from `dependency_reference_ids`), `priority`, `parallelizable`, `optional`, `approval_required`, and every token/cost estimate. None of these is inferred, derived, or defaulted from anything other than the record itself. The engine cannot trade a stage's type, reorder stages semantically, zero an estimate, remove parallelism or optionality, change `approval_required`, or add a model/tool/workflow reference a stage's own record did not already declare — there is simply no code path left that could do any of that.

`required_capabilities`, `required_modalities`, `success_criteria_reference_ids`, `fallback_reference_ids`, and `escalation_reference_ids` are **not** added to `ExecutionPlanStage` — that contract already transports every field this PR's own Objetivo names, and the spec explicitly forbids widening it unnecessarily. These five fields still round-trip correctly: they live on the `StageRecord` itself, which stays reachable through the request's own `stage_manifest_reference`, and `manifest_fingerprint` covers all of them, so any change to any of them changes `execution_plan_fingerprint` even though `ExecutionPlanStage` itself never carries them directly.

## StageManifestReference

`OrchestratorStageManifestReference` (`orchestrator-stage-manifest-reference.js`, 17 fields) is a new required field (`stage_manifest_reference`) on `ExecutionPlanRequest`. **O StageManifestReference é a fonte declarativa de verdade para a semântica de cada estágio.** It is tenant/organization/project/session/agent-bound, versioned, and fingerprinted (`manifest_fingerprint`), and carries `stage_ids` plus `stage_records[]` (an array of `StageRecord`) and `stage_count`.

Nothing in `context` can influence it — there is no side-channel for stage type, estimates, or parallelism, mirroring the same "no side-channel" discipline PR #98fix already established for dependency edges.

## StageRecord

`StageRecord` (27 fields) reuses PR #94's own `STAGE_TYPES` (`orchestrator-plan-stage.js`), `CAPABILITY_TYPES` (`model-capability-contract.js`), `MODALITIES` (`model-contract.js`), and the same nullable-reference/ordered-list/token/cost rules `OrchestratorPlanStage` already established, rather than redefining any of them. `task_reference_id` is required and non-nullable; `agent_reference_id`, `model_selection_reference_id`, `context_assembly_reference_id`, `memory_selection_reference_id`, and `workflow_reference_id` are nullable — a stage simply does not declare the references it does not use.

**Validated by construction, exactly like every reference this codebase has introduced since PR #97fix's `TaskReference`:** `buildStageRecord` computes `stage_fingerprint` over every other field, then validates, clones defensively, and deep-freezes — in that order, matching the spec's own required builder sequence. An invalid record (bad enum, negative priority, `estimated_total_tokens ≠ input + output`, a self-referencing dependency id, …) can never exist as a value.

## Ordem semântica

**A ordem semântica é `stage_sequence`, nunca alfabética.** `stage_ids` must represent the exact same order as `stage_records` — `isCanonicalStageSequenceOrder` enforces `stage_records[i].stage_sequence === i` for every `i`, which simultaneously guarantees non-negative, contiguous, unique, and ascending-in-array-order sequencing in one check. A duplicate `stage_id`, a duplicate `stage_sequence`, a sequence gap, or a `stage_ids` array that diverges from `stage_records`' own order are all rejected at construction time — never silently re-sorted. A two-stage manifest describing `stage-b` before `stage-a` is entirely legitimate and canonical, provided `stage-b`'s own `stage_sequence` is `0` and `stage-a`'s is `1`.

## Fingerprints dos stages e do manifesto

Each `StageRecord`'s own `stage_fingerprint` covers every field of that record except itself. `manifest_fingerprint` covers the whole manifest object — including the embedded `stage_records` array, and therefore every nested `stage_fingerprint` — except itself, using the same "whole object minus its own fingerprint field" pattern every fingerprinted reference in this codebase already uses.

Construction-time validation never recomputes a fingerprint to check it — only that it is present and well-formed. Tamper detection is exclusively an engine-level concern: `evaluateExecutionPlanRequest` recomputes `manifest_fingerprint` and every individual `stage_fingerprint` and compares them against the stored values, exactly mirroring PR #97fix's `TaskReference` and PR #98fix's `DependencyGraphReference` tamper checks. Any divergence — whether in the whole manifest or in a single stage — is `STAGE_MANIFEST_BLOCKED`, fail-closed.

## Integração com DependencyGraphReference

**O DependencyGraphReference permanece a fonte declarativa de verdade para as arestas do grafo.** `context.dependencyRecords` continues to be read nowhere in `execution-plan-engine.js`; a stale or malicious value there still has zero effect (verified directly by a dedicated test that exercises a scenario carrying a real dependency edge).

This PR adds a bidirectional equivalence check between the manifest and the graph: every dependency id any `StageRecord.dependency_reference_ids` names must exist in `dependency_graph_reference.dependency_records`, and every dependency record in the graph must be named by the `dependency_reference_ids` of the `StageRecord` whose `stage_id` equals that record's own `to_stage_id`. Either direction of disagreement is `STAGE_MANIFEST_BLOCKED`. A `PARALLEL_REFERENCE` edge additionally requires its target stage's own `parallelizable` to be `true` — a parallel dependency into a stage the Planner never marked parallelizable is `DEPENDENCY_BLOCKED`. A non-parallel edge whose `from_stage_id` sequence is not strictly before its `to_stage_id` sequence (i.e. a dependency that would run the Planner's own declared order backwards) is `DEPENDENCY_BLOCKED` too. Self-dependency and cycles remain structurally impossible, exactly as PR #98fix already established.

## Preservação de tokens e custos

Stage estimates are never zeroed and never re-derived: `estimated_input_tokens`, `estimated_output_tokens`, `estimated_total_tokens`, and `estimated_cost_minor_units` all come straight from each `StageRecord`, summed across every stage. These sums must agree **exactly** with `planning_result_reference.estimated_total_tokens`/`estimated_total_cost_minor_units`, with `orchestration_plan_reference`'s own copies of the same two fields, and with `execution_plan_budget`'s `estimated_total_tokens`/`estimated_total_cost_minor_units`/`estimated_input_tokens`/`estimated_output_tokens` — any disagreement is `BUDGET_BLOCKED`, never silently reconciled toward whichever source happened to be picked. The count of `MODEL_REFERENCE_STAGE`, `TOOL_REFERENCE_STAGE`, and `WORKFLOW_REFERENCE_STAGE` stages, and the count of `parallelizable` stages, are each cross-validated against `execution_plan_budget.maximum_model_stages`/`maximum_tool_stages`/`maximum_workflow_stages`/`maximum_parallel_stages` — exceeding any of them is `BUDGET_BLOCKED`.

## Package integrity: um fingerprint forte para o pacote inteiro

The old `execution_plan_fingerprint` covered only `execution_plan_id` and the list of stage ids — a genuinely weak fingerprint that two semantically very different plans could easily share. `execution-plan-package-integrity.js` introduces `buildExecutionPlanPackage` (35 fields) — a canonical payload covering every upstream fingerprint (authorization, orchestrator decision, readiness bundle, planning result, orchestration plan, task, stage manifest, dependency graph, budget, idempotency, memory, context, model, tool, workflow), every stage id and its own `stage_fingerprint` (in semantic, Planner-declared order — never re-sorted), every dependency/binding/stop-condition/compensation id-and-fingerprint pair (canonicalized by sorting the *pairs* together on id, so caller insertion order never matters but the id-to-fingerprint pairing is never broken), the estimate totals, `logical_sequence`, and the two simulation-safety flags. `computeExecutionPlanPackageFingerprint` is `stablePayload` over that whole package. A change to stage type, sequence, any per-stage reference, parallelism, optionality, approval, any estimate, any dependency, any binding, budget, idempotency, a stop condition, or a compensation reference all change `execution_plan_fingerprint` — verified directly by four dedicated fixture pairs (`package-fingerprint-stage-type-change`, `package-fingerprint-tokens-change`, `package-fingerprint-dependency-change`, `package-fingerprint-binding-change`), each compared against the same `valid-deterministic-stage-manifest` baseline.

## Bindings por estágio

Bindings are still built strictly from each stage's own record: a `MODEL_BINDING`/`TOOL_BINDING`/`WORKFLOW_BINDING`/`MEMORY_BINDING`/`CONTEXT_BINDING` is only ever created for a stage whose own `StageRecord` actually declares that reference — never for every stage, never speculatively. Each such binding's `binding_validated` additionally requires the record's declared reference id to equal the single reference the request actually carries for that type (a stage cannot silently point at "another" model, tool, or workflow); a mismatch is `BINDING_BLOCKED`.

**The `BUDGET_BINDING`'s own validity is deliberately decoupled from `execution_plan_budget.budget_validated`** — it is always `binding_validated=true`, since the binding only asserts that the plan is structurally bound to *a* budget reference. Whether that budget is itself within limits is checked separately, later, as its own `BUDGET_BLOCKED` — keeping the more specific status reachable rather than letting it be masked by the generic `BINDING_BLOCKED`, per this PR's own "usar status específico quando houver causa específica."

## Canonical fingerprint versus autenticidade

**stablePayload fornece canonicalização determinística. Ele não constitui assinatura ou garantia de autenticidade criptográfica.** It provides no MAC, no digital signature, no issuer identity, and no protection against a caller malicious enough to simply recompute the same payload. Every fingerprint in this PR — `stage_fingerprint`, `manifest_fingerprint`, `execution_plan_fingerprint` — is a canonical payload fingerprint, referred to exactly that way in this codebase, never as a signature. No key, secret, KMS, HMAC, digital signature, or real attestation is implemented here. Trusted attestation remains a future PR's concern.

## Precedência

The required precedence order places `STAGE_MANIFEST_BLOCKED` immediately after `EVIDENCE_BLOCKED` and before `BINDING_BLOCKED`, `FINGERPRINT_BLOCKED`, `VERSION_BLOCKED`, `BUDGET_BLOCKED`, `DEPENDENCY_BLOCKED`, `IDEMPOTENCY_BLOCKED`, `STOP_CONDITION_BLOCKED`, `COMPENSATION_BLOCKED`, `WAITING_APPROVAL_REFERENCE`, and `EXECUTION_PLAN_PREPARED_SIMULATION`. The engine honors this exactly: `stage_manifest_reference`'s own tenant/organization/project/session/agent bindings are checked in the same early block every other reference's bindings are (right after evidence/planning-result readiness, before version/fingerprint/budget/dependency), its structural cross-checks and fingerprint tamper detection run immediately after, and stages/bindings are now built and checked (`BINDING_BLOCKED`) *before* the fingerprint/version/budget/dependency steps that used to precede them in PR #98 — since stage data is now available immediately from the manifest, with no derivation step to wait for. See "Limitações" for the one deliberate, scoped deviation from the literal table this PR keeps.

**EXECUTION_PLAN_PREPARED_SIMULATION continua não executável e não autoriza nem inicia execução.** `executable`, `execution_authorized`, `execution_started`, `executed`, and `runtime_enabled` remain hardcoded `false` on every contract and result this PR can produce, including `PREPARED_SIMULATION`/`EXECUTION_PLAN_PREPARED_SIMULATION` and `WAITING_APPROVAL_REFERENCE`. **Nenhum agente, modelo, provider, ferramenta ou workflow é executado nesta implementação.**

## Registry

`execution-plan-registry.js` gains an eleventh store, `OrchestratorStageManifestReference`, reusing the identical `resolveRegistration`/`createEntityStore` precedence every other store already uses: validate → tenant → organization → replay → payload-mismatch → expected-version-conflict → expected-fingerprint-conflict → version-downgrade → accepted. Defensive clone and deep freeze are inherited from the shared `safe()`/`cloneFrozen` helpers, same as every other store.

## Auditoria

`execution-plan-audit.js` gains: `stage_manifest_reference_id`, `stage_manifest_fingerprint` (also folded into the existing `fingerprints` object under a new `stage_manifest` key), `stage_manifest_validated`, `stage_type_counts` (a label→count map, never full stage content), `parallel_stage_count`, `optional_stage_count`, `approval_stage_count`, `estimated_input_tokens`, `estimated_output_tokens`, and top-level `estimated_total_tokens`/`estimated_total_cost_minor_units` alongside the pre-existing `estimated_budget` object. It never records a full `StageRecord`, prompt, message, real memory content, operational parameter, response, secret, endpoint, or full payload — only ids, fingerprints, counts, and classification labels, exactly like every prior PR's audit trail.

`stage_manifest_validated` follows a different rule than `dependency_graph_validated`/`execution_plan_prepared` (both true only for `EXECUTION_PLAN_PREPARED_SIMULATION`): it is `true` for both `EXECUTION_PLAN_PREPARED_SIMULATION` **and** `WAITING_APPROVAL_REFERENCE`, since the approval gate is strictly the last check the engine runs — by the time a plan reaches it, every manifest-related structural check, fingerprint check, binding check, estimate cross-check, and dependency-graph equivalence check has already passed. `false` for every status reached before that point.

## Limitações

- **Precedence deviation, scoped and documented.** The literal required precedence table places `TENANT_BLOCKED`/`ORGANIZATION_BLOCKED`/`PROJECT_BLOCKED`/`SESSION_BLOCKED`/`TASK_BLOCKED` before `AUTHORIZATION_BLOCKED`/`EVIDENCE_BLOCKED`. This PR does not reorder those relative to the pre-existing PR #97/#98 authorization/evidence checks — doing so was outside this PR's own three numbered "Problemas obrigatórios" (stage reconstruction, metadata loss, weak fingerprint), and risked destabilizing already-tested PR #97/#98 precedence behavior for no benefit this PR's Objetivo asks for. `stage_manifest_reference`'s own tenant/organization/project/session checks run in the same early block every other reference's bindings already run in (right after evidence/planning-result readiness) — which is early enough to correctly precede `BINDING_BLOCKED`/`FINGERPRINT_BLOCKED`/`VERSION_BLOCKED`/`BUDGET_BLOCKED`/`DEPENDENCY_BLOCKED`/etc., satisfying the part of the table this PR's Objetivo is actually about.
- **`BUDGET_BINDING.binding_validated` was decoupled from `budget.budget_validated`.** See "Bindings por estágio" above — this was a genuine PR #98 coupling that only became observable once bindings started running before the budget check; keeping it coupled would have made every budget-invalid scenario report the generic `BINDING_BLOCKED` instead of the more specific `BUDGET_BLOCKED`.
- **`required_capabilities`/`required_modalities`/`success_criteria_reference_ids`/`fallback_reference_ids`/`escalation_reference_ids` are not added to `ExecutionPlanStage`.** See "Preservação 1:1 dos estágios" above — provenance is preserved via the manifest and its fingerprint, not by widening the stage contract.
- **The shared operational-material detector and `stablePayload` do not reliably catch `Map`/`Set`/`RegExp`/arbitrary class instances** (only `Date` is caught, via `stablePayload`'s own explicit `instanceof Date` check) — this is a pre-existing characteristic of `agent-identity-contract.js` shared by every PR since #85, not something introduced or fixed here; widening it was out of scope and outside this PR's own "modificar `agent-identity-contract.js` somente se um campo legítimo novo for bloqueado" instruction.
- **No cross-reference content resolution.** Like every prior orchestrator/evidence/authorization/execution-plan PR, this integration checks tenant/organization/project/session/plan consistency and status/fingerprint agreement, never that a referenced entity's content actually exists in a real store.

**A próxima etapa não deve ser o Execution Gateway ainda. A próxima etapa arquitetural é Execution Reference Binding and Authorization Provenance.**
