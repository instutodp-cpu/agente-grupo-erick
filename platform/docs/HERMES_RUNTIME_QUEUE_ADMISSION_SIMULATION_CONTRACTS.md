# Hermes Agent Core - Runtime Queue Admission Simulation Contracts

## Objetivo

Criar a camada declarativa de admissão em fila do Hermes, construída sobre um Dispatch Package já `DISPATCH_PACKAGE_PREPARED_SIMULATION` (PR #107). Recebe apenas o pacote `DISPATCH_PACKAGE_PREPARED_SIMULATION` (mais toda a cadeia Worker Assignment/Scheduler/Runtime que o sustenta) e produz uma representação declarativa de: quais Dispatch Intents preparadas seriam admissíveis em uma futura fila lógica; quais continuam aguardando dependência/aprovação; quais são apenas opcionais; quais estão bloqueadas por worker/capacidade/budget/policy/payload (herdado do Dispatch); qual fila lógica (Queue Class) seria compatível com cada intent; qual prioridade/partição lógica seria usada; a ordem determinística de admissão; quais quotas/limites de backlog se aplicariam; quais policies de tenant/organização/projeto/sessão/agente permanecem preservadas; quais intents seriam aceitas/rejeitadas/adiadas/mantidas fora da fila; quais referências seriam encaminhadas a uma futura Queue Materialization Simulation; quais blockers impediriam a preparação; e qual envelope declarativo seria preparado para a próxima camada — nunca fila real, nunca item de fila, nunca inserção, nunca mensagem publicada, nunca job criado, nunca posição reservada, nunca quota consumida, nunca backlog alterado, nunca lease, nunca worker reservado/iniciado, nunca conexão aberta, nunca processo/thread criado, nunca container/scheduler iniciado, nunca dispatch autorizado/aplicado/enviado.

"QUEUE_ADMISSION_PACKAGE_PREPARED_SIMULATION significa somente que intents de dispatch foram avaliadas contra filas lógicas, quotas, backlog, partições e fairness. Nenhuma fila ou item de fila foi criado."

## Dispatch Package ≠ Queue Admission Package

`DISPATCH_PACKAGE_PREPARED_SIMULATION` (PR #107) prova que, para cada estágio elegível de um Worker Assignment Package já preparado, uma intenção declarativa de dispatch foi avaliada e, quando possível, preparada — nunca definiu se essa intenção seria efetivamente admissível em uma fila lógica futura (compatibilidade de fila, quotas por tenant/organização/projeto/agente, backlog disponível, partição, fairness determinística). `QUEUE_ADMISSION_PACKAGE_PREPARED_SIMULATION` é a camada seguinte: recebe um Dispatch Package já preparado como pré-condição obrigatória e produz exclusivamente uma representação declarativa de admissão por intent — nunca fila, nunca item, nunca enqueue, nunca posição, nunca quota consumida.

Distinção preservada explicitamente em todo o código e testes:

```
DISPATCH_PACKAGE_PREPARED_SIMULATION ≠ QUEUE_ADMISSION_PACKAGE_PREPARED_SIMULATION
  ≠ QUEUE_MATERIALIZATION_PACKAGE_PREPARED_SIMULATION ≠ QUEUE_CREATED ≠ QUEUE_ITEM_CREATED
  ≠ QUEUE_ITEM_ENQUEUED ≠ JOB_CREATED ≠ DISPATCH_AUTHORIZED ≠ WORKER_RESERVED
  ≠ STAGE_DISPATCHED ≠ STAGE_STARTED ≠ EXECUTED
```

## Runtime Queue Admission Policy

`runtime-queue-admission-policy.js` (66 campos exatos). Nenhuma policy pode habilitar fila, enqueue ou execução real: os 18 `require_*` e os 18 `fail_on_*`/`fail_closed` são estruturalmente forçados `true`; `allow_external_effect_reference=false` e `allow_irreversible_reference=false` são permanentes; `allow_queue_admission_package_preparation_simulation=true` é permanente. Os 11 `allow_*` (no-LLM/model/tool/workflow/parallel/shared/dedicated/optional/retry/dead-letter/state-change queue reference) são genuinamente configuráveis. Os 11 `maximum_*` (entradas de admissão total/model/tool/workflow/parallel, por tenant/organização/projeto/agente, tokens/custo estimado) são limites reais comparados contra contagens honestamente agregadas durante a avaliação — aplicados exclusivamente às entradas genuinamente `QUEUE_ADMISSION_ACCEPTED_SIMULATION`, nunca a entradas adiadas, aguardando ou bloqueadas.

## Referências declarativas de fila

`runtime-queue-class-reference.js` (49 campos exatos) materializa um catálogo de filas lógicas candidatas: `queue_class_type` (6 valores: `SHARED`/`DEDICATED`/`TENANT`/`ORGANIZATION`/`PROJECT`/`AGENT_QUEUE_REFERENCE`), `queue_priority_class` (5), `queue_partition_strategy` (7), `queue_fairness_strategy` (4), `queue_retry_class` (3), escopo opcional (tenant/organização/projeto/agente), tipos de estágio/capacidades/modalidades/providers/models/tools/workflows suportados, e flags `supports_*`. `supports_external_effect`/`supports_irreversible` são permanentemente forçados `false` — nenhuma fila lógica pode declarar suporte a efeito externo ou irreversível, mesmo que o input de build tente declará-lo `true`. `queue_created`/`queue_class_applied` são sempre `false`.

"Queue Class Reference é uma descrição declarativa. Ela não comprova que uma fila, tópico, broker ou consumer real existe."

`runtime-queue-capacity-snapshot-reference.js` e `runtime-queue-quota-reference.js` compartilham a mesma aritmética por-dimensão (`maximum_X`/`current_X`/`available_X`, com `available_X === maximum_X - current_X`) já estabelecida em toda a linhagem para 8 dimensões (backlog/inflight-ou-admissão/parallel/model/tool/workflow/tokens/cost). A Capacity Snapshot descreve uma fila lógica inteira (`runtime_queue_class_reference_id`); a Quota Reference descreve um teto por escopo único — `SCOPE_FIELDS` (`tenant_id`/`organization_id`/`project_id`/`agent_id`) exige que exatamente um seja preenchido, nunca múltiplos simultâneos, refletindo que quotas são avaliadas "por: tenant; organização; projeto; agente" como referências independentes, uma por escopo. `capacity_applied`/`capacity_reserved`/`queue_backlog_changed`/`quota_applied`/`quota_reserved`/`quota_consumed` são sempre `false`.

`runtime-queue-partition-reference.js` deriva `partition_key_type` estruturalmente a partir de `partition_strategy` (mapa 1:1 `STRATEGY_TO_KEY_TYPE`) — nunca declarado independentemente pelo caller; um `partition_key_type` que não corresponda à `partition_strategy` é rejeitado. A chave de partição em si (`partition_key_value`) é derivada apenas de identidade canônica (tenant/organização/projeto/agente) ou de composição de estágio (tipo/capacidades) — nunca de conteúdo de prompt ou mensagem. `queue_created`/`queue_item_created`/`partition_applied` são sempre `false`.

`runtime-queue-fairness-reference.js` carrega 5 ranks determinísticos (`tenant_admission_rank`/`organization_admission_rank`/`project_admission_rank`/`agent_admission_rank`/`global_admission_rank`), derivados exclusivamente de `priority_class` + `dispatch_sequence` + identidade canônica — nunca de relógio real, `Date`, timer ou valor aleatório. `fairness_applied`/`queue_position_reserved` são sempre `false`.

"A fairness é determinística, não utiliza relógio real, random ou side-channel."

`runtime-queue-intent-binding-reference.js` liga um Dispatch Intent a Queue Class/Partition/Quota/Capacity Snapshot através de 6 flags de match (`queue_class_match`/`partition_match`/`quota_match`/`capacity_match`/`fairness_match`/`freshness_match`); `intent_binding_validated` só é `true` quando `dispatch_intent_status === DISPATCH_INTENT_PREPARED_SIMULATION` E todas as 6 flags são `true` — consistência bidirecional verificada pelo próprio validador.

"Somente Dispatch Intents com status DISPATCH_INTENT_PREPARED_SIMULATION podem ser aceitas."

`runtime-queue-admission-entry-reference.js` (14 valores de `admission_status`) materializa, por Dispatch Intent, o resultado final de admissão. `queue_admission_validated` só é `true` quando `admission_status === QUEUE_ADMISSION_ACCEPTED_SIMULATION` E os 8 `*_gate_passed` são simultaneamente verdadeiros. `queue_admission_applied`/`queue_created`/`queue_item_created`/`queue_item_enqueued`/`queue_position_reserved` são sempre `false`, mesmo para uma entrada aceita.

"QUEUE_ADMISSION_ACCEPTED_SIMULATION não constitui enqueue, reserva de posição ou consumo de quota."

`runtime-queue-admission-order-reference.js` preserva a ordem genuína de `ordered_dispatch_intent_reference_ids`/`ordered_queue_admission_entry_reference_ids` — derivada diretamente de `runtime_dispatch_package_reference.ordered_dispatch_intent_reference_ids` (PR #107), nunca da ordem meramente declarada pelo array de intents recebido. As 5 listas de partição (`accepted`/`deferred`/`waiting`/`optional`/`blocked_queue_admission_entry_reference_ids`) particionam completamente a lista ordenada, sem sobreposição e sem lacuna. `queue_admission_order_applied` é sempre `false`.

`runtime-queue-admission-replay-reference.js` (próprio deste layer — nunca a Dispatch Replay Reference reutilizada "como se fosse" Queue Admission Replay) prova, por ID+fingerprint+digest, vínculo genuíno ao Dispatch Package e à Dispatch Replay Reference que esta avaliação está usando, mais ao mesmo `idempotency_reference` da cadeia. `replay_allowed` é derivado (`expected_queue_admission_attempt <= maximum_queue_admission_attempts && duplicate_queue_admission_preparation_blocked !== true`), nunca declarado livremente pelo caller. `replay_consumed` é sempre `false`. `omitQueueAdmissionReplayReference` (exportado por `runtime-queue-admission-request.js`) exclui apenas este campo do cálculo do fingerprint do próprio Queue Admission Request — a mesma exclusão canônica já estabelecida para Replay References em toda a linhagem, resolvendo a circularidade auto-referencial.

## Runtime Queue Admission Request

`runtime-queue-admission-request.js` (39 campos exatos) agrega toda a cadeia Dispatch + Worker Assignment + Scheduler + Runtime já preparada (reutilizada verbatim, nunca contratos paralelos): as 8 listas de referência por-estágio do Dispatch (Stage/Worker-Binding/Dependency-Gate/Approval-Gate/Capacity/Budget/Payload/Intent), a Dispatch Order/Replay, os 4 catálogos novos desta camada (Queue Class/Capacity-Snapshot/Quota/Partition), Capacity Snapshot/Concurrency/Budget/Freshness/Idempotency/Registry-Snapshot já preparados, as policies oficiais de Network/Secret e os Stage Policy Requirements/Scheduler Dependencies já produzidos pelo Dispatch (reutilizados verbatim, nunca re-derivados), mais a própria `runtime_queue_admission_policy` e `runtime_queue_admission_replay_reference`. `simulation_context` nunca é lido para nenhuma decisão.

### Prova de não-substituição por fingerprint/ID-set

A Queue Admission Request não recarrega a proveniência bruta que o Dispatch já validou — em vez disso, o boundary prova que as 8 listas por-estágio, a Order, a Replay, as Scheduler Dependencies, os Stage Policy Requirements e as policies oficiais de Network/Secret que a request de fato carrega produzem exatamente o mesmo conjunto de IDs/fingerprints já registrado no `RuntimeDispatchPackage` — nunca uma lista independentemente substituída pelo caller. `idSetMatches`/`fingerprintSetMatches` (`runtime-queue-admission-boundary.js`, reutilizadas verbatim do mesmo padrão de `runtime-dispatch-boundary.js`) implementam essa prova.

## Seleção determinística de Queue Class

`selectQueueClass(stage, ctx)` filtra o catálogo de Queue Classes por: `queue_class_active === true`; nunca uma classe com efeito externo/irreversível (estruturalmente impossível, já que `supports_external_effect`/`supports_irreversible` são permanentemente `false`); escopo (tenant/organização/projeto/agente nulo-ou-igual, `agent_scope_ids` vazio-ou-contendo); `supported_stage_types` contém o tipo do estágio; `required_capabilities`/`required_modalities` do estágio são subconjunto de `supported_capability_ids`/`supported_modality_ids`; `supports_model`/`supports_tool`/`supports_workflow` exigidos somente quando o estágio realmente usa model/tools/workflow; `supports_optional` exigido somente se `stage.optional === true`; `supports_parallel` exigido somente se `stage.parallelizable === true`; `supports_state_change` exigido somente se a classificação de efeito colateral do estágio for `STATE_CHANGE_REFERENCE`; deve ter uma Capacity Snapshot e ao menos uma Quota Reference correspondentes. As sobreviventes são ordenadas deterministicamente por: especificidade da classe (dedicated/project/agent antes de organization/tenant antes de shared); `queue_priority_class`; capacidade disponível (backlog/inflight/parallel/tokens/cost, decrescente); backlog atual (crescente); e, por fim, `runtime_queue_class_reference_id` (ordem lexicográfica) como desempate final — nunca `Date.now()`, `Math.random()` ou qualquer side-channel.

## Admissão sequencial gulosa (greedy)

A ordem de fairness é computada uma única vez para todas as Dispatch Intents `DISPATCH_INTENT_PREPARED_SIMULATION` (chave de ordenação: `[priority_rank, dispatch_sequence]`, ascendente). O boundary então itera essa ordem, mantendo cópias de trabalho locais (nunca persistidas, nunca aplicadas aos objetos reais) da capacidade disponível de cada Queue Class e da quota disponível de cada Quota Reference relevante (cujo único campo de escopo não-nulo corresponde à identidade canônica da avaliação). Para cada intent: se a quota relevante for insuficiente em qualquer uma das 8 dimensões → `QUEUE_ADMISSION_DEFERRED_QUOTA_REFERENCE`; senão, se a capacidade da Queue Class for insuficiente → `QUEUE_ADMISSION_DEFERRED_BACKLOG_REFERENCE`; senão → `QUEUE_ADMISSION_ACCEPTED_SIMULATION`, e as cópias de trabalho são decrementadas para a próxima iteração. Isso implementa genuinamente "usar somas das accepted entries" — nunca comparar cada entry isoladamente contra o teto total, capturando o caso em que múltiplas entradas cabem individualmente mas excedem o total em conjunto.

Toda Dispatch Intent que não está `DISPATCH_INTENT_PREPARED_SIMULATION` (waiting-dependency/waiting-approval/optional/no-worker/capacity/budget/policy/blocked) recebe uma Queue Admission Entry mapeada estruturalmente 1:1 do seu próprio `dispatch_intent_status` — nunca admitida, mas sempre presente na Order.

## Runtime Queue Admission Package / Decision / Result / Audit

`runtime-queue-admission-package.js` (103 campos exatos) é o envelope final imutável: IDs upstream de toda a cadeia (Dispatch/Worker-Assignment/Scheduler/Runtime-Execution/Order/Replay), as 7 listas de referências derivadas por ID desta camada (ordenadas, sem duplicata), as 2 listas de ordem genuína, as 5 listas de partição, 10 contagens agregadas, 4 estimativas (tokens/custo — somadas apenas sobre entradas genuinamente aceitas), 13 fingerprints upstream únicos, 19 listas de fingerprints derivados (as 12 já herdadas do Dispatch Package mais 7 novas desta camada: `queue_class_fingerprints`/`queue_capacity_snapshot_fingerprints`/`queue_quota_fingerprints`/`queue_partition_fingerprints`/`queue_fairness_fingerprints`/`queue_intent_binding_fingerprints`/`queue_admission_entry_fingerprints`), e `queue_admission_package_fingerprint`/`_digest` recalculados (mesmo padrão de dois campos excluídos progressivamente já estabelecido em toda a linhagem).

"QUEUE_ADMISSION_PACKAGE_PREPARED_SIMULATION significa somente que intents de dispatch foram avaliadas contra filas lógicas, quotas, backlog, partições e fairness. Nenhuma fila ou item de fila foi criado."

`runtime-queue-admission-decision.js` define seu próprio vocabulário de 27 status (21 próprios + os 6 de identidade já reutilizados de toda a linhagem), com sua própria `QUEUE_ADMISSION_PRECEDENCE_ORDER` e `STATUS_OUTCOME_MAP` — separado, nunca fundido ao vocabulário de nenhuma camada anterior. 22 flags `*_validated` mapeiam 1:1 nas seções de cross-check do boundary; apenas uma se torna verdadeira em conjunto com o outcome (`queue_admission_package_prepared_in_simulation`), enquanto toda flag operacional (`queue_admission_applied`, `queue_created`, `queue_item_created`, `queue_item_enqueued`, `queue_position_reserved`, `job_created`, `dispatch_authorized`, `worker_reserved`, `stage_dispatched`, etc. — 16 flags na Decision) permanece sempre `false`. `runtime-queue-admission-result.js` é um envelope mais amplo (29 flags operacionais seguras — soma as 16 da Decision a `dispatch_acknowledged`, `dispatch_lease_created`, `worker_connection_opened`, `worker_process_created`, `worker_thread_created`, `container_started`, `stage_completed`, `stage_failed`, `runtime_enabled`, `execution_authorized`, `execution_started`, `network_used`, `secret_resolved`), o mesmo padrão de dois níveis já estabelecido entre Decision/Result em toda a linhagem.

`runtime-queue-admission-audit.js` registra apenas IDs/fingerprints/digest, status/decision/next_state, bindings de identidade, IDs de Queue Class/Partition/Quota, `entry_counts`, `priority_classes`, `backlog_summary`, `fairness_rank_outcomes` (formatados como `<id>#rank_<n>`, nunca com separador `::` que colidiria com o padrão de endereço local `::1` do scanner de material operacional), `estimate_summary`, blockers, reason codes, logical sequence — **nunca payload completo, prompt, mensagem, memória, segredo, credencial, argumentos de tool ou código.**

## pr108fix — correções da revisão

A auditoria da versão inicial desta PR aprovou a arquitetura geral, a pré-condição de Dispatch, a Queue Admission Replay própria, os contratos declarativos, a admissão agregada, as partições, a integridade do package, a segurança e os testes locais, mas exigiu quatro correções obrigatórias antes de prosseguir.

**FIX 1 — Queue Class valida provider/model/tool/workflow reais, não apenas `supports_*`.** `selectQueueClass`/`evaluateQueueClassCompatibility` (`runtime-queue-admission-boundary.js`) derivam os requisitos reais de cada stage a partir dos seus `RuntimeWorkerStagePolicyRequirementReference` genuinamente `RESOLVED_FROM_OFFICIAL_REFERENCE` — nunca de um hint não confiável. Para MODEL, o `source_reference_id` do requisito é o `decision_id` de um `ModelSelectionDecision` oficial; como o Dispatch layer nunca recarrega esse objeto adiante (só prova que o fingerprint do requisito não mudou), esta camada introduz o novo campo `official_model_selection_decision_references` na Queue Admission Request — os objetos `ModelSelectionDecision` reais, cada um cross-validado por ID+fingerprint (`stablePayload`) contra o requisito RESOLVED correspondente — para obter `selected_provider_id`/`selected_model_id` genuínos. Para TOOL/WORKFLOW, o próprio `source_reference_id` já É o tool/workflow ID (estrutura herdada de `deriveStagePolicyRequirements`, PR #106), então nenhum objeto adicional é necessário. Um requisito ausente ou `UNRESOLVED_REFERENCE` nunca autoriza nada.

"Queue Class compatibility valida os IDs reais de provider, model, tools e workflow, não apenas flags supports_*."

Cada tool que o stage exige é verificada independentemente — nenhuma interseção parcial é aceita (uma única tool não suportada já invalida a classe inteira para aquele stage). Uma lista `supported_model_provider_ids`/`supported_model_ids`/`supported_tool_ids`/`supported_workflow_ids` vazia nunca é tratada como wildcard — apenas reduz a `includes()` a sempre falso, fail-closed por construção, sem necessidade de um caso especial. Reason codes: `queue_class_model_provider_mismatch`, `queue_class_model_id_mismatch`, `queue_class_tool_id_mismatch::<tool_id>`, `queue_class_workflow_id_mismatch`, `queue_class_stage_requirement_unresolvable`.

**FIX 2 — Coleção completa de quotas por tenant/organização/projeto/agente.** Uma Queue Class só se torna candidata quando o boundary consegue montar, a partir de `runtime_queue_quota_references`, uma coleção com exatamente uma quota por escopo (`classifyQuotaScope` deriva o escopo do único campo de identidade não-nulo de cada quota) — as quatro genuinamente vinculadas à identidade canônica desta avaliação, sem duplicata e sem escopo divergente. `quotaCollectionByClassId` (calculado uma única vez por avaliação) só registra uma classe quando as quatro estão presentes e corretas; qualquer ausência, duplicata ou identidade divergente exclui a classe inteira dos candidatos.

"Uma Queue Class só é elegível quando possui a coleção completa de quotas exigidas por tenant, organização, projeto e agente."

`RuntimeQueueIntentBindingReference`/`RuntimeQueueAdmissionEntryReference` não carregam mais um único `runtime_queue_quota_reference_id` escolhido arbitrariamente — ambos agora transportam `runtime_queue_quota_reference_ids`, a coleção completa (4 IDs, ordenados e deduplicados) que participou da decisão, automaticamente coberta pelo fingerprint de cada contrato (`intent_binding_fingerprint`/`admission_entry_fingerprint` já cobrem todos os próprios campos). A admissão sequencial gulosa usa exatamente essa mesma coleção de 4 quotas (nunca um subconjunto filtrado por heurística) para a aritmética por-dimensão. Reason codes: `queue_tenant_quota_missing`/`queue_organization_quota_missing`/`queue_project_quota_missing`/`queue_agent_quota_missing` (expostos coletivamente como `queue_quota_collection_incomplete` na razão de rejeição agregada por candidato).

**FIX 3 — Somente `FIFO_WITHIN_PRIORITY_REFERENCE` é operacionalmente implementada.** `FAIRNESS_STRATEGIES_IMPLEMENTED` (`runtime-queue-admission-boundary.js`) contém hoje um único valor. Uma Queue Class que declara `STRICT_PRIORITY_WITH_TENANT_FAIRNESS`, `WEIGHTED_ROUND_ROBIN_REFERENCE` ou `DETERMINISTIC_FAIR_SHARE_REFERENCE` nunca é selecionada — se essa for a ÚNICA razão pela qual nenhum candidato foi encontrado para um stage, a entrada recebe o status dedicado `QUEUE_ADMISSION_FAIRNESS_BLOCKED` (adicionado a `ADMISSION_STATUSES`) em vez do bucket genérico `QUEUE_ADMISSION_QUEUE_CLASS_BLOCKED`, com reason `queue_fairness_strategy_not_implemented::<strategy>`.

"Nesta versão, somente FIFO_WITHIN_PRIORITY_REFERENCE é implementada. As demais fairness strategies permanecem reservadas e bloqueadas fail-closed."

Os 4 valores continuam declarados no enum `QUEUE_FAIRNESS_STRATEGIES` (`runtime-queue-class-reference.js`) para uma versão futura, mas apenas FIFO passa pela avaliação de compatibilidade. A ordenação real (`priority_rank` + `dispatch_sequence`) nunca simulou tenant fairness/weighted round robin/deterministic fair share — nomeá-la corretamente como FIFO evita reivindicar uma semântica não implementada.

**FIX 4 — Queue Capacity Snapshot é reavaliada na sequência lógica da própria Queue Admission Request.** O boundary nunca mais confia isoladamente em `capacity_validated`/`snapshot_expired_logically` do próprio snapshot — `validCapacityClassIds` (calculado uma única vez por avaliação) recomputa, para cada snapshot, `snapshotExpiredAtAdmission = (request.logical_sequence - snapshot.logical_sequence) > snapshot.snapshot_valid_sequences`, exige `request.logical_sequence >= snapshot.logical_sequence` (nunca regressiva) e `capacity_available === true`. Uma classe cujo único snapshot correspondente falha essa reavaliação nunca se torna candidata; se essa for a ÚNICA razão de nenhum candidato ter sido encontrado, a entrada recebe `QUEUE_ADMISSION_CAPACITY_BLOCKED` com reason `queue_capacity_snapshot_not_valid_at_admission`.

"Queue Capacity Snapshot é reavaliada na sequência lógica do Queue Admission Request."

**Package Integrity.** O novo campo `official_model_selection_decision_fingerprints` (lista ordenada, deduplicada) em `runtime-queue-admission-package.js` garante que alterar qualquer Model Selection Decision oficial consultada durante a seleção de Queue Class altera ou bloqueia `queue_admission_package_fingerprint`/`_digest`. Os fingerprints de Queue Class/Quota/Capacity Snapshot/Stage Policy Requirement já participavam do package desde a versão inicial desta PR; a identidade de tool/workflow já está inteiramente coberta por `stage_policy_requirement_fingerprints` (seu próprio `source_reference_id` É o tool/workflow ID).

## Runtime Queue Admission Boundary

`runtime-queue-admission-boundary.js`'s `evaluateRuntimeQueueAdmissionRequest(request, context)` segue a ordem de precedência estabelecida (identidade antes de policy, cadeias upstream antes de derivação local):

1-2. Request/toda referência aninhada contra seu validador oficial.
3. Queue Admission Policy marcada (limites aplicados após a derivação por-intent).
Identidade (`checkIdentity`, mesma função de toda a linhagem), avaliada cedo para casar a precedência real.
4-7. Cadeia de Dispatch genuinamente `DISPATCH_PACKAGE_PREPARED_SIMULATION` (status/flags/IDs encadeados, incluindo `dispatch_authorized`/`worker_reserved`/`stage_dispatched` ainda `false`) mais a prova de não-substituição por fingerprint/ID-set de todas as 8 listas por-estágio, a Order, a Replay, as Scheduler Dependencies, os Stage Policy Requirements e as policies oficiais.
18-19. Reafirmação de que nenhuma policy oficial de Network/Secret é `PRODUCTION`.
19. Freshness recalculada na sequência do próprio Queue Admission Request.
20. Queue Admission Replay — prova de vínculo genuíno ao Dispatch Package/Dispatch Replay/idempotency que esta avaliação está usando.
21. Idempotency reutilizado verbatim da Dispatch Request, self-fingerprint recomputado.
22. Registry Snapshot — mesmo snapshot que o Dispatch Package já vinculou (ou ausência consistente em ambas as camadas).
26-28. Queue Class/Capacity Snapshot/Quota — bindings 1:1 cruzados (nenhuma Capacity Snapshot duplicada por classe), cada Capacity Snapshot referenciada genuinamente `capacity_validated`.
29-35. Derivação por intent, iterando a ordem canônica do Dispatch Package (`ordered_dispatch_intent_reference_ids`, nunca a ordem declarada pelo array recebido): seleção de Queue Class → derivação de partição → fairness → admissão sequencial gulosa (ver acima) → Intent Binding → Admission Entry. Toda intent não-preparada recebe uma Admission Entry mapeada estruturalmente do seu `dispatch_intent_status`.
35. Queue Admission Order — subsequência genuína da ordem canônica do Dispatch Package, particionada por status final de admissão.
36. Limites de policy aplicados exclusivamente às entradas aceitas (contagem total/model/tool/workflow/parallel, tokens/custo estimado, por-tenant).
42. Invariantes de não-execução (`dispatch_result.executed`/`dispatch_package.executed` ainda `false`).

Emissão final de Package/Decision/Result/Audit. Qualquer inconsistência bloqueia fail-closed.

## pr108fix2 — correções da segunda reauditoria

A reauditoria do HEAD `c6161c1db86f75a9f9c2045920871be82b6a9578` aprovou o cross-check de provider/model/tool/workflow, a coleção completa de quotas, os quatro quota IDs no Intent Binding e Admission Entry, a fairness limitada honestamente a FIFO, a freshness de Capacity Snapshot recalculada, a admissão agregada, a integridade do package e a segurança operacional — e apontou dois fixes finais.

**FIX 1 — Todos os quatro limites por identidade participam da decisão.** `RuntimeQueueAdmissionPolicy` declara `maximum_per_tenant_admission_count`/`maximum_per_organization_admission_count`/`maximum_per_project_admission_count`/`maximum_per_agent_admission_count`, mas o boundary só aplicava o primeiro. Os quatro agora são comparados independentemente contra `acceptedCount` (o mesmo valor, já que esta avaliação é sempre single-identity), cada um com seu próprio reason code (`queue_admission_per_tenant_count_exceeds_policy_limit`/`_organization_`/`_project_`/`_agent_count_exceeds_policy_limit`) e status `QUEUE_ADMISSION_POLICY_BLOCKED` — nunca agrupados em um reason genérico.

**FIX 2 — A ordem decisória é a mesma ordem registrada na Queue Admission Order.** A admissão gulosa não reordena mais as intents preparadas por `priority_rank`/`dispatch_sequence` antes de admiti-las — ela itera `canonicalIntentOrder` (a própria `ordered_dispatch_intent_reference_ids` do Dispatch Package) filtrada às intents `DISPATCH_INTENT_PREPARED_SIMULATION`, preservando a posição relativa exatamente como o Dispatch Package já a registrou.

"A Queue Admission processa entries na mesma ordem canônica registrada no RuntimeQueueAdmissionOrderReference. A ordem usada para distribuir capacidade e quotas nunca diverge da ordem incluída no package."

As quatro flags de preservação de ordem são hoje genuinamente recomputadas, cada uma como um gate independente que bloqueia `QUEUE_ADMISSION_ORDER_BLOCKED` — nunca afirmadas `true` por construção:

- `dispatch_order_preserved` (`queue_admission_dispatch_order_not_preserved`): re-verifica, entrada por entrada, que a Admission Entry na posição N de `ordered_queue_admission_entry_reference_ids` corresponde exatamente à intent na posição N de `canonicalIntentOrder`.
- `priority_order_preserved` (`queue_admission_priority_order_not_preserved`): como a ordem canônica do Dispatch nunca é mais reordenada por prioridade de Queue Class, esta flag verifica que a sequência de `priority_rank` induzida por essa ordem já é não-decrescente — se uma Queue Class exigisse uma prioridade incompatível com a ordem já registrada, o boundary bloqueia a avaliação inteira em vez de reordenar silenciosamente e afirmar preservação.
- `fairness_order_preserved` (`queue_admission_fifo_order_not_preserved`): para `FIFO_WITHIN_PRIORITY_REFERENCE`, verifica que, dentro de cada grupo de mesma `priority_rank` (contíguo ou espalhado na ordem canônica), `dispatch_sequence` é estritamente crescente.
- `required_predecessor_order_preserved` (`queue_admission_required_predecessor_order_violation::<scheduler_dependency_reference_id>`): reutiliza as próprias `RuntimeSchedulerDependencyReference` já carregadas e cross-validadas (nunca uma fonte paralela); para cada aresta `required === true` cujos dois extremos participam desta Queue Admission Order, exige `position(predecessor) < position(target)` na mesma ordem que será registrada.

`checkPriorityOrderPreserved`/`checkFairnessOrderPreserved` (`runtime-queue-admission-boundary.js`) são funções puras, exportadas e diretamente testáveis, recebendo apenas a lista de entradas já em ordem canônica — nunca um score aleatório, relógio real ou timer.

`admission_sequence` continua único por entrada genuinamente aceita, atribuído na mesma ordem canônica em que a admissão gulosa avaliou e consumiu as cópias locais de quota/capacidade; entradas não aceitas recebem o valor "quantidade de entradas aceitas até este ponto" — uma semântica explícita e determinística, nunca ambígua entre ordem de avaliação e ordem de aceitação.

## pr108fix3 — correções da terceira reauditoria

A reauditoria do HEAD `b5c407ae4d712bfca8768147dca593208a3e7d88` aprovou o cross-check real de Queue Class, as quotas completas nos quatro escopos, os quatro limites por identidade, a fairness limitada a FIFO, a freshness dos Queue Capacity Snapshots, a ordem canônica do Dispatch, a recomputação de prioridade/FIFO/predecessor, a integridade de package em geral e a segurança operacional — e apontou dois fixes finais.

**FIX 1 — Um blocker de Queue Class precede um blocker de Order.** `checkPriorityOrderPreserved`/`checkFairnessOrderPreserved` eram executados sobre `withQueueClass` inteiro, incluindo intents sem `selectedClass` (que usavam `PRIORITY_RANK.BACKGROUND_REFERENCE` como prioridade sintética). Isso podia produzir `QUEUE_ADMISSION_ORDER_BLOCKED` antes do `QUEUE_ADMISSION_QUEUE_CLASS_BLOCKED`/`CAPACITY_BLOCKED`/`FAIRNESS_BLOCKED` genuíno da própria entrada, mascarando o problema real. O boundary agora constrói `orderEligibleEntries = withQueueClass.filter(entry => entry.selectedClass !== null)` e executa as duas provas somente sobre essa lista — uma intent sem classe compatível nunca mais contribui com uma prioridade sintética para as provas de ordem, e nunca causa um bloqueio de ordem em nome de outra entrada. A prova `dispatch_order_preserved` continua cobrindo todas as entries (aceitas ou não); a prova `required_predecessor_order_preserved` continua usando as posições da ordem canônica diretamente (nunca dependeu de `withQueueClass`/`fairnessOrder`), logo nenhuma das duas precisou de ajuste.

**FIX 2 — Registry Snapshot obrigatório no caminho preparado.** Antes, um Dispatch Package sem Registry Snapshot oficial (`registry_snapshot_fingerprint='fingerprint_not_available'`) combinado com `registry_snapshot_reference=null` na própria Queue Admission Request ainda alcançava `QUEUE_ADMISSION_PACKAGE_PREPARED_SIMULATION`, marcando `registry_snapshot_validated=true` e propagando o placeholder para o package — contradizendo `require_registry_snapshot_valid=true` (permanentemente forçado na Queue Admission Policy). Agora, para qualquer resultado preparado, um Registry Snapshot oficial genuíno é obrigatório e passa por seis checagens independentes, cada uma com seu próprio reason code e status `QUEUE_ADMISSION_REGISTRY_SNAPSHOT_BLOCKED`:

- ausência (Dispatch Package sem snapshot, ou `registry_snapshot_reference=null` nesta camada): `queue_admission_registry_snapshot_missing`;
- auto-consistência do fingerprint (`computeSnapshotFingerprint` recomputado): `queue_admission_registry_snapshot_fingerprint_mismatch` — já reforçada estruturalmente pelo próprio validador do contrato reutilizado verbatim, que rejeita a construção da Request antes mesmo do boundary avaliar;
- vínculo com o Dispatch Package (`snapshot_fingerprint === dispatchPackageRef.registry_snapshot_fingerprint`): `queue_admission_registry_snapshot_not_bound_to_dispatch`;
- escopo (`tenant_id`/`organization_id`/`project_id` batendo com a identidade canônica): `queue_admission_registry_snapshot_scope_mismatch`;
- sequência lógica não regressiva em relação a esta admissão (`request.logical_sequence >= registrySnapshotRef.logical_sequence`): `queue_admission_registry_snapshot_stale`;
- `snapshot_validated`/`snapshot_consistent` genuinamente `true` (o primeiro é uma declaração do caller nunca forçada estruturalmente pelo próprio contrato — só este boundary a exige): `queue_admission_registry_snapshot_not_validated`.

Nenhum placeholder `fingerprint_not_available` alcança mais `queue_admission_package_fingerprint`/`_digest` em um package `QUEUE_ADMISSION_PACKAGE_PREPARED_SIMULATION` — o placeholder só aparece honestamente em outcomes já bloqueados por outro motivo, nunca fingindo uma validação que não ocorreu. O bundle de teste (`test/helpers/runtime-queue-admission-simulation-test-data.js`) agora reutiliza verbatim o mesmo `buildOfficialRegistrySnapshot()` já estabelecido pela camada de Worker Assignment (pr106fix5), vinculando-o simultaneamente ao slot próprio da Worker Assignment Request e ao slot próprio da Dispatch Request — as duas camadas imediatamente abaixo continuam tratando Registry Snapshot como opcional ("quando existentes"), mas agora sempre o recebem no caminho feliz, para que o Dispatch Package chegue com um `registry_snapshot_fingerprint` genuíno que esta camada possa exigir.

## pr108fix4 — correções da quarta reauditoria

A reauditoria do HEAD `b9b51f055bc8af3297bb8a41769a3744207a95cd` aprovou todos os fixes anteriores, incluindo intents sem Queue Class excluídas das provas priority/FIFO, os quatro limites por identidade, a ordem canônica do Dispatch, as quotas completas, os Queue Class resource IDs reais, a capacity freshness, o Registry Snapshot obrigatório, a integridade de package em geral e zero efeitos operacionais — e apontou um único fix final.

**Gate flags representam avaliações independentes.** Antes, `RuntimeQueueIntentBindingReference`/`RuntimeQueueAdmissionEntryReference` derivavam várias flags diretamente do `admissionStatus` final (`capacity_match = admissionStatus === ACCEPTED`, `fairness_match`/`freshness_match` sempre `true`, todos os gates da Entry `false` para qualquer status não aceito) — perdendo evidência válida: uma entry `DEFERRED_QUOTA`, por exemplo, podia genuinamente ter Queue Class válida, partição válida, capacidade válida, fairness válida e freshness válida, com apenas a quota insuficiente, mas o contrato registrava tudo como se nada tivesse passado.

"Gate flags registram resultados independentes. Um status deferred não apaga gates anteriores que já foram aprovados."

Agora, cada um dos 8 gates é computado independentemente, uma única vez por intent, contra `gateClass` — a classe genuinamente selecionada (`selectedClass`) quando existe, ou, apenas quando nenhuma foi genuinamente selecionada, a melhor candidata `structurallyCompatibleClass`: aquela desqualificada somente por capacidade/freshness/fairness (dimensões com gate próprio), nunca por incompatibilidade estrutural genuína (escopo, tipo de estágio, capacidades, modalidades, IDs reais de provider/model/tool/workflow, ou coleção de quota incompleta — esta última permanece estrutural, já que uma classe sem a coleção completa nunca é candidata utilizável para nada). `selectQueueClass` retorna ambas (`selectedClass`/`structurallyCompatibleClass`) a partir da mesma avaliação de `evaluateQueueClassCompatibility`, nunca uma segunda passada redundante.

- `queue_class_gate_passed = gateClass !== null` — reflete compatibilidade estrutural, independente de capacidade/freshness/fairness/quota-fit.
- `partition_gate_passed = queueClassGatePassed && chave de partição derivável para gateClass`.
- `quota_gate_passed`/`capacity_gate_passed = partitionGatePassed && peekQuotaFits/peekCapacityFits(gateClassId, requested)` — funções puras de leitura (`peekCapacityFits`/`peekQuotaFits`, `runtime-queue-admission-boundary.js`), reutilizadas tanto pela tentativa real de admissão (mutante) quanto pela evidência do gate (nunca mutante), garantindo que os dois nunca divirjam quando `gateClass === selectedClass`.
- `fairness_gate_passed = queueClassGatePassed && gateClass.queue_fairness_strategy ∈ FAIRNESS_STRATEGIES_IMPLEMENTED` — o único ponto em que a estratégia de fairness de `structurallyCompatibleClass` é genuinamente consultada, já que essa é a única dimensão sua própria seleção ignorou deliberadamente.
- `freshness_gate_passed = queueClassGatePassed && validCapacityClassIds.has(gateClassId)`.
- `replay_gate_passed`/`idempotency_gate_passed = validatedFlags.replay_validated/idempotency_validated === true` — gates globais já validados (com retorno antecipado em caso de falha) antes de qualquer derivação por-intent começar, portanto genuinamente `true` sempre que este ponto do código é alcançado.

Quando `selectedClass !== null` (intent genuinamente admissível ou tentada), `gateClass` é sempre o mesmo objeto — garantindo estruturalmente que toda entry `QUEUE_ADMISSION_ACCEPTED_SIMULATION` carrega os 8 gates `true` sem necessidade de bookkeeping adicional, e que `capacity_gate_passed`/`quota_gate_passed` de uma entry `DEFERRED_*` refletem o estado real (não hardcoded) da OUTRA dimensão que não causou o deferral.

O validador de `RuntimeQueueAdmissionEntryReference` agora também exige consistência específica por status — nunca todos os gates, apenas o que o próprio status nomeia: `QUEUE_ADMISSION_DEFERRED_QUOTA_REFERENCE` exige `quota_gate_passed=false`; `QUEUE_ADMISSION_DEFERRED_BACKLOG_REFERENCE` exige `capacity_gate_passed=false`; `QUEUE_ADMISSION_FAIRNESS_BLOCKED` exige `fairness_gate_passed=false`; `QUEUE_ADMISSION_QUEUE_CLASS_BLOCKED` exige `queue_class_gate_passed=false` (e, por não haver `structurallyCompatibleClass` quando a coleção de quota está incompleta, todos os outros gates também ficam `false` nesse caso específico, coincidindo com o exemplo da própria especificação).

Os fingerprints de Intent Binding, Admission Entry e Queue Admission Package já cobriam todos os próprios campos (via `stablePayload` sobre o objeto inteiro, exceto o próprio campo de fingerprint) — alterar qualquer gate genuíno já altera ou bloqueia esses fingerprints automaticamente, sem necessidade de nenhuma alteração estrutural adicional nos três contratos.

## pr108fix5 — confirmação da precedência Queue Class/Capacity/Fairness antes de Order

Uma auditoria referenciando o HEAD anterior a `pr108fix3` reapontou o mesmo risco que `pr108fix3` FIX 1 já havia fechado: uma intent sem Queue Class genuinamente selecionada nunca mais contribui com uma prioridade sintética para `checkPriorityOrderPreserved`/`checkFairnessOrderPreserved` (`orderEligibleEntries = fairnessOrder.filter(entry => entry.selectedClass !== null)`, em vigor desde `pr108fix3` e preservado através de `pr108fix4`). Esta seção documenta a confirmação e os cenários adicionais de teste que solidificam essa garantia — nenhuma alteração de código foi necessária, apenas cobertura de teste adicional para os cenários mistos de duas intents que o design de catálogo único de Queue Class por request torna impossível de construir via o boundary completo (capacidade/fairness são propriedades da classe, não de uma intent individual, então não é possível ter uma intent bloqueada por capacidade e outra genuinamente admitida na MESMA avaliação usando a mesma classe) — provados em vez disso diretamente contra `selectQueueClass`/as funções de prova de ordem, exatamente como o próprio boundary as deriva.

`admission_sequence` já documentava a semântica correta antes desta revisão: único e crescente para toda entrada genuinamente aceita, na ordem real em que a admissão gulosa avaliou e consumiu as cópias locais; uma entrada não aceita recebe o valor "quantidade de entradas aceitas até este ponto" — nunca uma posição reservada, nunca ambíguo entre ordem de avaliação e ordem de aceitação.

## Limitações

- **Ranks de fairness por escopo (tenant/organização/projeto/agente) são hoje triviais**: como este boundary avalia apenas as intents de uma única identidade canônica (tenant/organização/projeto/agente) por request, `tenantRanks`/`organizationRanks`/`projectRanks`/`agentRanks` sempre coincidem com `globalRanks` na prática — uma característica estrutural do design atual, não algo exercitado diferentemente, documentada honestamente em vez de escondida.
- Nenhum worker real, processo, thread, container, fila, tópico, broker, consumer, job, cron, timer, retry, polling ou child_process é usado ou referenciado em qualquer módulo desta PR. Nenhuma rede é usada e nenhum segredo é resolvido em nenhum caminho desta avaliação.
