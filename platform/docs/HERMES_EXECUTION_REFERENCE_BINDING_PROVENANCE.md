# Hermes Agent Core - Execution Reference Binding and Authorization Provenance

## Objetivo

PR #98's own minimal `AuthorizationDecisionReference` (23 fields) never carried `actor_id`, `actor_role`, `authorization_scope_id`, `approval_reference_id`, `budget_authorization_id`, `expiration_evaluation_id`, or any of the five sub-fingerprints PR #97's full `AuthorizationDecision` (70 fields) already has. **O Execution Plan transporta a proveniência completa da autorização que permitiu sua preparação.** This PR closes that gap with `AuthorizationProvenanceReference`, and closes two adjacent gaps at the same time: `execution_scope_reference_id` on `ExecutionPlanContract` used to be a placeholder pointing at the plan's own `execution_plan_id` (never a real authorized scope), and `context.currentRegistryVersion` was the last side-channel this engine ever read for a decisional condition.

**O campo execution_scope_reference_id aponta para o AuthorizationScopeReference real, nunca para o próprio Execution Plan.** `AuthorizationScopeReference` — a minimal, positive-allowlist mirror of PR #97's own `AuthorizationScope` — now travels through `ExecutionPlanRequest` as a required field, and `execution_scope_reference_id` is fixed to reference it.

**Nenhuma condição decisória é lida de context.** `ExecutionRegistrySnapshotReference` replaces `context.currentRegistryVersion` with a versioned, fingerprinted snapshot of every entity version this evaluation depends on, carried as a required request field exactly like every other reference PR #94-#99 already established this discipline for.

## AuthorizationProvenanceReference

`AuthorizationProvenanceReference` (`execution-authorization-provenance-reference.js`, 41 fields) carries the full chain: `authorization_decision_id`/`authorization_request_id`/`authorization_policy_id`/`authorization_scope_id`, `actor_id`/`actor_role`, `approval_reference_id`, `budget_authorization_id`, `expiration_evaluation_id`, `planning_result_id`/`plan_id`/`task_reference_id`, `agent_id`/`tenant_id`/`organization_id`/`project_id`/`session_reference_id`, and a sub-fingerprint for every one of those ten identity fields (`authorization_decision_fingerprint`, `authorization_request_fingerprint`, `authorization_policy_fingerprint`, `authorization_scope_fingerprint`, `actor_fingerprint`, `approval_fingerprint`, `budget_authorization_fingerprint`, `expiration_fingerprint`, `planning_result_fingerprint`, `orchestration_plan_fingerprint`, `task_fingerprint`), plus lineage (`created_from_reference_id`/`parent_reference_id`, both nullable — a root provenance reference has no prior reference to point to — and `derived_from_reference_ids`, an ordered unique list).

**This is the one contract in this PR series with no self-fingerprint field.** `authorization_provenance_fingerprint` never appears in its own exact-fields list; the fingerprint the plan/result/package need is always computed externally by the engine (`safeFingerprint(provenanceRef)`), the same way `memory_fingerprint`/`context_fingerprint` already are for other referenceless-fingerprint decision objects.

`provenance_validated` is a genuine, caller-set boolean — this contract's own structural validator cannot compute it, since doing so requires cross-checking data (the rest of the request) the contract has no access to. `execution-plan-engine.js`'s own cross-checks are what actually decide whether it *should* be `true` for a given plan; the reference merely carries the caller's declaration, type-checked as a boolean.

## AuthorizationScopeReference

`AuthorizationScopeReference` (`execution-authorization-scope-reference.js`, 32 fields) reuses PR #97's own `RISK_CLASSIFICATIONS`, `WILDCARD_FREE_PATTERN`, and `isOrderedUniqueEnumList` from `execution-authorization-scope.js` rather than redefining them, but is not identical to `AuthorizationScope`: it adds `allowed_model_reference_ids`/`allowed_capability_types`/`allowed_stage_types` (none of which the full `AuthorizationScope` has) and renames `allowed_task_types` to `allowed_task_reference_ids` — a list of genuine task reference ids, not a `TASK_TYPES` enum list.

**A scope reference is a positive allowlist.** An empty list on any `allowed_*` field means nothing of that kind is permitted, never "no restriction" — the same principle PR #97 already established. `cross_tenant_allowed`/`cross_organization_allowed`/`cross_project_allowed`/`cross_session_allowed` are forced `false`.

`execution-reference-binding-validator.js`'s `validateScopeCrossChecks` checks, in order: the scope's own `authorization_decision_id` and canonical tenant/organization/project/session/agent identity; `allowed_plan_ids` includes the plan; `allowed_task_reference_ids` includes the task; `allowed_agent_ids` includes the agent; every stage record's own `model_selection_reference_id`/`tool_reference_ids`/`workflow_reference_id` (when declared) is inside the corresponding allowlist; every stage record's own `stage_type` is inside `allowed_stage_types`; every capability the stage record's own `required_capabilities` lists is inside `allowed_capability_types` (**pr100fix FIX 1** — this check was dormant until now: `allowed_capability_types` existed on the contract from the start, but nothing cross-checked it against `StageRecord.required_capabilities`, so a scope with an empty `allowed_capability_types` never actually blocked a capability-requiring stage); the task's `risk_classification` is inside `allowed_risk_classifications`; the budget's estimated totals are within `maximum_authorized_tokens`/`maximum_authorized_cost_minor_units`; and the scope agrees with the provenance reference on `authorization_scope_id`. A stage record whose `model_selection_reference_id`/`workflow_reference_id` is `null` is simply not checked against the model/workflow allowlist — the same null-tolerant pattern PR #95's own engine already established for optional references. A missing capability blocks with `AUTHORIZATION_SCOPE_BLOCKED`/`scope-capability-blocked::<capability>`, naming the specific capability that was not in the allowlist.

## ExecutionRegistrySnapshotReference

`ExecutionRegistrySnapshotReference` (`execution-registry-snapshot-reference.js`, 20 fields) carries `expected_registry_version`/`observed_registry_version`, and two fixed-key-set plain objects — `registry_entity_versions` (integer values) and `registry_entity_fingerprints` (string values) — over the exact same seven-entry key set, `REGISTRY_ENTITY_KEYS`: `execution_plan_request`, `stage_manifest`, `dependency_graph`, `provenance`, `scope`, `execution_plan_budget`, `idempotency_policy`. **Never a Map** — both objects are validated as exact-key-set plain objects, satisfying the requirement that they correspond 1:1 to the versioned entities this evaluation depends on without ever accepting an arbitrary caller-chosen key set. (`provenance`/`scope` are deliberately bare, not `authorization_provenance`/`authorization_scope` — the longer forms trip the same forbidden-key segment scan every `authorization_*` field name in this codebase has to navigate; see `agent-identity-contract.js`.)

`snapshot_consistent` is never caller-asserted independently of the two version fields it summarizes — the validator recomputes `expected_registry_version === observed_registry_version` and rejects any declared value that disagrees, and the builder computes it directly rather than trusting `input.snapshot_consistent`. The engine's own `validateSnapshotCrossChecks` additionally compares each of the seven `registry_entity_fingerprints` entries against a value it computes fresh at evaluation time: `stage_manifest`/`dependency_graph`/`scope`/`execution_plan_budget`/`idempotency_policy` against those references' own self-declared fingerprint fields, and `provenance` against `safeFingerprint(provenanceRef)` (external, since the reference carries none of its own).

**`execution_plan_request` is fingerprinted over the request's own shallow identity fields only** — `execution_plan_request_id`/`_version`, `correlation_id`, `causation_id`, `trace_id`, `logical_sequence`, `expected_registry_version`, `validator_version` — never the entire request object. Every nested reference the request carries already has its own dedicated tamper check elsewhere (this snapshot's own other six entities, plus `task_fingerprint`/`plan_fingerprint`/etc. checked directly by the engine), so re-fingerprinting all of them again here would add nothing except size: a fingerprint of the whole request would embed every one of those nested fingerprints as an escaped string value, which then gets embedded *again* once this snapshot's own `snapshot_fingerprint` is used anywhere downstream — and PR100 originally did exactly that during development, producing multi-hundred-KB `plan_fingerprint`/`execution_plan_fingerprint` values per scenario before this was caught and fixed. Every fingerprint in this codebase fingerprints one bounded record for exactly this reason; this one now does too.

## Cross-checks: idempotência, stop conditions, compensações

`execution-reference-binding-validator.js`'s `buildReferenceLevelBindingRecords` resolves each of idempotency/stop-condition/compensation through a dedicated `resolve*BindingOutcome` function (`resolveIdempotencyBindingOutcome`, `resolveStopConditionBindingOutcome`, `resolveCompensationBindingOutcome`), checked in this fixed order, never `VALIDATED_SIMULATION` on id agreement alone (**pr100fix FIX 3**):

1. **Version.** The reference's own real declared version (`idempotency_reference_version`, `stop_condition_version`, `compensation_reference_version` — never a hardcoded `1`) must be a positive integer, or the binding is `VERSION_BLOCKED`. `BindingRecord.source_reference_version` on these three binding types now always carries that real version.
2. **Self-fingerprint recompute-and-compare.** Each reference's own compute function — `computeIdempotencyFingerprint`, `computeStopConditionFingerprint`, `computeCompensationFingerprint`, all reused directly from their existing contracts, none redefined — is recomputed and compared against the reference's own declared fingerprint field. A mismatch is `FINGERPRINT_BLOCKED`, never masked by a later, more generic check. This closes a real gap: before this fix, a idempotency/stop-condition/compensation reference that had been tampered with after being fingerprinted, but whose `execution_plan_id`/`execution_stage_id` still happened to agree with the plan, was classified `VALIDATED_SIMULATION`.
3. **Tenant/organization/project/session** (idempotency only — stop conditions and compensations carry no independent tenant scope of their own beyond the plan they target).
4. **Plan/stage/authorization-decision id agreement**, and (idempotency only) `plan_fingerprint`/`idempotency_validated` — a mismatch here, with every earlier check already passing, is `CONFLICT_BLOCKED`.

A failure at any layer never blocks the whole evaluation directly — it sets that one reference-level `BindingRecord`'s own `binding_status`, which makes `all_bindings_validated` (and therefore `references_bound_in_simulation`) `false` on the `BindingLedger`, which the engine translates into `REFERENCE_BINDING_BLOCKED`. **Bindings são validados, mas nunca aplicados nesta implementação** — every failure is recorded with a specific `reason_codes` entry (`idempotency-version-invalid`, `idempotency-self-fingerprint-mismatch`, `idempotency-plan-mismatch`, `idempotency-authz-mismatch`, `idempotency-fingerprint-mismatch`, `idempotency-not-validated`, `stop-condition-version-invalid`, `stop-condition-self-fingerprint-mismatch`, `stop-condition-plan-mismatch`, `stop-condition-stage-mismatch`, `compensation-version-invalid`, `compensation-self-fingerprint-mismatch`, `compensation-plan-mismatch`, `compensation-stage-mismatch`) on the offending `BindingRecord`, never silently dropped or corrected.

## BindingRecord and BindingLedger

`BindingRecord` (`execution-reference-binding-record.js`, 29 fields) generalizes PR #98's own `ExecutionPlanStageBinding` (18 fields, 12 binding types) with a genuine source/target distinction, `authorization_scope_id`, and a richer 11-value `binding_status` vocabulary (`VALIDATED_SIMULATION`, `BINDING_BLOCKED`, `FINGERPRINT_BLOCKED`, `VERSION_BLOCKED`, `TENANT_BLOCKED`, `ORGANIZATION_BLOCKED`, `PROJECT_BLOCKED`, `SESSION_BLOCKED`, `SCOPE_BLOCKED`, `CONFLICT_BLOCKED`, `VALIDATION_FAILED`) over an 18-value `binding_type` enum (the original 12 plus `AUTHORIZATION_SCOPE_BINDING`, `AUTHORIZATION_PROVENANCE_BINDING`, `IDEMPOTENCY_BINDING`, `STOP_CONDITION_BINDING`, `COMPENSATION_BINDING`, `REGISTRY_SNAPSHOT_BINDING`, `DEPENDENCY_GRAPH_BINDING`, `STAGE_MANIFEST_BINDING`). `binding_validated` is tied one-way to `binding_status` — `true` only when `binding_status === 'VALIDATED_SIMULATION'`, `false` for every other status — the two fields can never disagree, and `binding_record_fingerprint` is recomputed and compared, fail-closed, the same proactive pattern this PR applies to every new self-fingerprinted contract from the start (learned from PR #99fix's own retroactive fix).

`execution-reference-binding-validator.js`'s `buildBindingLedgerForPlan` never re-derives stage-level binding logic: every already-computed `ExecutionPlanStageBinding` (task/agent/memory/context/model/tool/workflow/authorization/budget, unchanged from PR #98) is wrapped 1:1 into a `BindingRecord` — source and target collapse to the same single reference, since the older contract never had a distinct target concept. Reference-level `BindingRecord`s are then appended for the scope, the provenance chain, the registry snapshot, the stage manifest, the dependency graph, idempotency, one per stop condition, and one per compensation reference — always at plan scope (`execution_stage_id = null`).

**Every reference-level binding record (scope, provenance, registry snapshot, stage manifest, dependency graph) carries a compact SHA-256 content digest of the entire validated reference object as `source_reference_fingerprint`, not a partial summary (pr100fix FIX 2).** An earlier version of this PR used a hand-picked subset of each reference's own shallow fields for these five bindings, to avoid re-embedding each reference's own (already sizeable) canonical fingerprint through `BindingRecord` → `BindingLedger` → `ExecutionPlanPackage` → plan/result/audit. A GitHub-MCP architecture audit correctly flagged that as a real defect: a partial summary means `source_reference_fingerprint` no longer represents the reference's actual content, so a change to any field the summary excluded would go completely undetected by the binding record itself. `computeCanonicalContentDigest` (`canonical-content-digest.js`) replaces both the original full-fingerprint approach and the partial-summary regression: a fixed ~71-character `sha256:<hex>` digest of the object's canonical payload, full-fidelity (any field changing anywhere in the object changes the digest) and compact (no compounding through downstream layers, regardless of how large the referenced object is). See "Canonical content digest" below.

`BindingLedger` (`execution-reference-binding-ledger.js`, 32 fields, 12 `ledger_status` values) consolidates every `BindingRecord` this evaluation produced. `binding_count`/`required_binding_count`/`validated_binding_count`/`blocked_binding_count`/`all_bindings_validated` are all derived from `binding_records` and cross-checked by the validator — never independently caller-asserted, the same derived-boolean discipline `snapshot_consistent` and `execution_plan_prepared` already established. `all_required_bindings_present` is the one field this contract cannot derive from `binding_records` alone (it depends on knowing which binding types *should* exist, information only the engine has) and remains a type-checked caller declaration.

**REFERENCES_BOUND_SIMULATION significa apenas que as referências declarativas foram vinculadas e validadas. Nenhuma execução foi autorizada ou iniciada.** `references_bound_in_simulation` — on both the ledger and, separately, the result — is `true` only when every required binding is both present and validated; `bindings_applied`, `execution_authorized`, and `execution_started` are forced `false` regardless.

## ExecutionReferenceBindingResult and audit

`ExecutionReferenceBindingResult` (`execution-reference-binding-result.js`, 21 fields) is a thin envelope over the ledger this evaluation already produced — `status` reuses the ledger's own 12-value vocabulary, `references_bound_in_simulation` is tied one-way to `status === 'REFERENCES_BOUND_SIMULATION'`, and `result_fingerprint` is recomputed and compared, fail-closed. `execution-reference-binding-audit.js` records only ids, fingerprints (`provenance`/`scope`/`snapshot`/`ledger`), status, counts (`binding_count`/`required_binding_count`/`validated_binding_count`/`blocked_binding_count`), the seven bindings (tenant/organization/project/session/agent/actor/scope), `logical_sequence`, `reason_codes`, and the simulation-only flags — never a full `BindingRecord` payload, mirroring `execution-plan-audit.js`'s own restraint.

`execution-plan-audit.js` itself gains `authorization_provenance_fingerprint`/`authorization_scope_fingerprint`/`registry_snapshot_fingerprint`/`binding_ledger_fingerprint` (folded into the existing `fingerprints` object, as bare `provenance`/`scope` keys for the same forbidden-key-segment reason as the snapshot reference above), `validated_binding_count`/`blocked_binding_count` (folded into `counts`), and top-level `references_bound_in_simulation`.

## ExecutionPlanRequest / Contract / Result

`ExecutionPlanRequest` gains three required fields — `authorization_provenance_reference`, `authorization_scope_reference`, `registry_snapshot_reference` — bringing it to 30 fields. `ExecutionPlanContract` gains 8 fields (61 total): `authorization_provenance_reference_id`/`authorization_provenance_fingerprint`, `authorization_scope_reference_id`/`authorization_scope_fingerprint`, `registry_snapshot_reference_id`/`registry_snapshot_fingerprint`, `binding_ledger_id`/`binding_ledger_fingerprint`, and fixes `execution_scope_reference_id` as described above. `ExecutionPlanResult` gains 13 fields (85 total): the same 8 id/fingerprint pairs plus `authorization_provenance_validated`/`authorization_scope_validated`/`registry_snapshot_validated`/`binding_ledger_validated`/`references_bound_in_simulation`. The four `_validated` booleans follow `stage_manifest_validated`'s own rule (`true` for both `EXECUTION_PLAN_PREPARED_SIMULATION` and `WAITING_APPROVAL_REFERENCE`, since the approval gate runs strictly last); `references_bound_in_simulation` follows `execution_plan_prepared`'s stricter rule (`true` only for the terminal prepared state — a plan still waiting for approval has not yet had its bound references confirmed ready for anything beyond preparation).

`execution-plan-package-integrity.js`'s `buildExecutionPlanPackage` gains 6 fields (41 total): `authorization_provenance_fingerprint`, `authorization_scope_fingerprint`, `registry_snapshot_fingerprint`, `binding_ledger_fingerprint`, and `binding_record_ids`/`binding_record_fingerprints` (canonicalized as an id/fingerprint pair set, like every other unordered list in the package). A change to any of the four new fingerprints, or to any binding record, changes `execution_plan_fingerprint`.

Four new statuses join both `EXECUTION_PLAN_STATUSES` (29 total) and `RESULT_STATUSES` (25 total): `AUTHORIZATION_PROVENANCE_BLOCKED`, `AUTHORIZATION_SCOPE_BLOCKED`, `REGISTRY_SNAPSHOT_BLOCKED`, `REFERENCE_BINDING_BLOCKED`.

## Precedência

Provenance, scope, and registry-snapshot are validated as a contiguous block immediately after the pre-existing tenant/organization/agent/project/session bindings and blocked-decision checks (memory/context/model/tool/workflow), and before plan/planning-result id agreement, the stage-manifest cross-check block, stage materialization, bindings, budget, dependency-graph checks, idempotency, stop conditions, and compensations. `REFERENCE_BINDING_BLOCKED` is evaluated last among the blocking gates — right after compensations, immediately before the approval gate — since the binding ledger wraps every stage-level binding and every reference-level cross-check this evaluation already performed. This is a documented, scoped judgment call in the same spirit as PR #99's own precedence compromise: the pre-existing PR #96-99 gates keep their relative order, and the four new gates are inserted as two contiguous blocks rather than a full positional reorder against every already-tested regression fixture. See "Limitações".

**A próxima etapa arquitetural é Validation Semantics and Architecture Gates, não o Execution Gateway.**

## Registry

`execution-reference-binding-registry.js` adds six new private, in-memory-only stores — provenance references, scope references, registry snapshots, binding records, binding ledgers, binding results — each built with the identical `createEntityStore`/`resolveRegistration` precedence every registry in this codebase already uses: validate → tenant → organization → replay → payload-mismatch → expected-version-conflict → expected-fingerprint-conflict → version-downgrade → accepted. No persistence; defensive clone and deep freeze throughout, inherited from the same `safe()`/`cloneFrozen` pattern `execution-plan-registry.js` already established.

## Canonical content digest (pr100fix FIX 2)

`canonical-content-digest.js` exports `computeCanonicalContentDigest(value)`: canonicalize with `stablePayload`, hash with `node:crypto`'s `createHash('sha256')`, and return `sha256:<hex>`. Only `node:crypto` is used — no HMAC, no secret material, no network call, no private key, no real attestation, matching the same restriction every other fingerprint in this codebase already observes.

- **The canonical payload fingerprint continues to exist.** `stablePayload` alone, used everywhere else in this codebase (`scope_fingerprint`, `manifest_fingerprint`, `snapshot_fingerprint`, ...), is unchanged by this fix. The digest is an *additional*, compact representation for the specific case of a `BindingRecord` referencing an already-fingerprinted object.
- **The digest is compact.** A fixed ~71-character string regardless of the input object's size — closing the compounding-through-downstream-layers problem entirely, without losing coverage (unlike the partial-summary approach it replaces).
- **The digest is not a signature.** It proves two canonicalized payloads are byte-identical; it proves nothing about who produced either one.
- **The digest does not prove the identity of the emitter.** No key, secret, or credential is involved in producing it.
- **The digest is not a trusted attestation.** A caller who can recompute the same canonical payload can trivially reproduce the same digest.

Invalid or non-serializable content (a cyclic reference, for instance) fails sanitized — `digest_invalid::<message>` — never throwing an uncaught exception, the same fail-closed-but-sanitized discipline `safeFingerprint` already established in `execution-plan-engine.js`/`execution-reference-binding-validator.js`.

## Canonical fingerprint versus autenticidade

**stablePayload fornece canonicalização determinística. Ele não constitui assinatura ou garantia de autenticidade criptográfica.** Every fingerprint this PR introduces — `authorization_provenance_fingerprint` (computed externally, since the reference carries none of its own), `scope_fingerprint`, `snapshot_fingerprint`, `binding_record_fingerprint`, `ledger_fingerprint`, `result_fingerprint` — is a canonical payload fingerprint, referred to exactly that way, never as a signature. No key, secret, KMS, HMAC, or real attestation is implemented here. The same is true, separately, of `computeCanonicalContentDigest`'s own SHA-256 digest — see "Canonical content digest" above.

## Confirmação de nenhuma execução real

Every new contract forces `simulation=true`/`production_blocked=true`, and `execution_authorized`/`execution_started`/`bindings_applied`/`snapshot_applied`/`provenance_applied`/`scope_applied`/`binding_applied` are all hardcoded `false` regardless of status. **Nenhum agente, modelo, provider, ferramenta ou workflow é executado nesta implementação.** No `fetch`/`http`/`https`/`net`/`tls`/`child_process`/`eval`/`new Function`/`process.env`/dynamic import appears anywhere in the nine new files this PR introduces.

## Limitações

- **Precedence deviation, scoped and documented.** See "Precedência" above — this PR inserts its four new gates as two contiguous blocks rather than reordering every pre-existing PR #96-99 gate against the literal 24-step table, for the same reason PR #99 made its own analogous compromise: minimizing destabilization of already-tested precedence behavior outside this PR's own scope.
- **Approval, actor, policy, authorization-request, and expiration sub-fingerprints on `AuthorizationProvenanceReference` continue to be transported provenance claims, not independent attestations, while the corresponding minimal references (`ApprovalReference`, an actor identity reference, an `AuthorizationPolicyReference`, an `AuthorizationRequestReference`, an `ExpirationEvaluationReference`) are not themselves supplied to `ExecutionPlanRequest`.** `approval_fingerprint`/`actor_fingerprint`/`authorization_policy_fingerprint`/`authorization_request_fingerprint`/`expiration_fingerprint` are declared, structurally validated as non-empty strings, and carried forward faithfully — but, unlike `authorization_decision_fingerprint`/`authorization_scope_fingerprint`/`budget_authorization_fingerprint`/`planning_result_fingerprint`/`orchestration_plan_fingerprint`/`task_fingerprint` (each cross-checked against a real sibling reference already present in the request), these five have no sibling reference in this PR's own request shape to recompute-and-compare against. A future PR introducing those five minimal reference contracts would close this gap the same way PR #100 closed PR #98's own analogous gap.
- **`idempotency_policy_reference.request_fingerprint` is not cross-checked against the live request.** It predates this PR's own registry-snapshot envelope and has no canonical request-identity fingerprint to compare against yet in this codebase; `execution_plan_id`/`authorization_decision_id`/`plan_fingerprint` are cross-checked, `request_fingerprint` is not. A future PR may bind it once one exists.
- **`registry_entity_versions` are not independently incremented per entity in this PR** — every entity is versioned `1` by construction in every fixture this PR ships; the contract supports arbitrary positive integers per entity, but nothing in this PR's own scope exercises version skew between entities.
- **No cross-reference content resolution.** Like every prior orchestrator/evidence/authorization/execution-plan PR, this integration checks tenant/organization/project/session/plan consistency and status/fingerprint agreement, never that a referenced entity's content actually exists in a real store.
- **The shared operational-material detector and `stablePayload` do not reliably catch `Map`/`Set`/`RegExp`/arbitrary class instances** (only `Date` is caught) — a pre-existing characteristic of `agent-identity-contract.js` shared by every PR since #85, not something introduced or fixed here.
