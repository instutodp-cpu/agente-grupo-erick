# Hermes Agent Core - Runtime Execution Simulation Contracts

## Objetivo

A PR #102 termina em `GATEWAY_ACCEPTED_SIMULATION` — um pacote de Execution Plan que o Gateway aceitou para simulação, mas sem nenhum contrato que descreva o que seria efetivamente entregue a um runtime futuro. Esta PR cria esses contratos declarativos: recebe um pacote já aceito pelo Gateway e materializa um **Runtime Execution Package** que descreve quais estágios seriam simulados, em qual ordem, quais dependências existiriam, quais capacidades seriam necessárias, quais modelos/ferramentas/workflows seriam referenciados, quais limites de token e custo seriam aplicáveis, quais condições de parada seriam consideradas, quais compensações seriam referenciadas, quais artefatos declarativos poderiam ser produzidos, e quais eventos simulados seriam esperados. O resultado máximo é `RUNTIME_PACKAGE_PREPARED_SIMULATION`.

**RUNTIME_PACKAGE_PREPARED_SIMULATION significa apenas que um pacote declarativo de runtime foi preparado. Nenhuma admissão, autorização ou execução ocorreu.**

## Gateway acceptance ≠ Runtime package preparation

`GATEWAY_ACCEPTED_SIMULATION` (PR #102) é uma checagem estrutural e de policy sobre um pacote de Execution Plan — nunca decide nada sobre um runtime. `RUNTIME_PACKAGE_PREPARED_SIMULATION` (esta PR) é uma camada inteiramente nova, um passo além: materializa as referências específicas e minimizadas que um runtime futuro consumiria (Runtime Stage Manifest, Runtime Dependency Manifest, Runtime Budget/Stop/Compensation/Artifact/Event references) — nunca o Execution Plan bruto. Preparar esse pacote **não** significa admiti-lo: a futura PR #104 (Runtime Readiness and Admission Boundary) é responsável por decidir admissão. Nenhum destes dois status implica o outro; são preservados como conceitos distintos em todo o código e em todo o vocabulário de status (`RUNTIME_PACKAGE_PREPARED_SIMULATION` ≠ `RUNTIME_ADMITTED_SIMULATION` ≠ `RUNTIME_ENABLED` ≠ `EXECUTION_AUTHORIZED` ≠ `EXECUTION_STARTED` ≠ `EXECUTED`).

## Runtime Execution Simulation Policy

`runtime-execution-simulation-policy.js` (39 campos exatos) segue a mesma forma que `execution-gateway-policy.js` já estabeleceu: quase inteiramente `SAFE_FLAGS` forçados, com apenas 6 campos genuinamente configuráveis pelo chamador (`allow_no_llm_stage`, `allow_model_reference_stage`, `allow_tool_reference_stage`, `allow_workflow_reference_stage`, `allow_parallel_reference`, `allow_human_approval_reference`). `allow_state_change_reference` é forçado `true`, mas apenas como **referência declarativa** — nunca habilita uma mudança de estado real (ver "Compensações" abaixo). `allow_external_effect_reference`/`allow_irreversible_reference` permanecem forçados `false`; qualquer stage classificado como tal bloqueia incondicionalmente (`RUNTIME_POLICY_BLOCKED`), independentemente da policy.

## Runtime Execution Simulation Request

`runtime-execution-simulation-request.js` (30 campos exatos, 30 desde pr103fix FIX #3) agrega toda referência necessária — Gateway Decision/Result/Package Reference, Execution Plan/Result, Stage Manifest, Dependency Graph, Binding Ledger, Validation Ledger, Authorization Provenance/Scope, Registry Snapshot, `execution_budget_reference` (ver "Runtime Budget"), e as 7 referências de runtime (`runtime_stage_manifest_reference`, `runtime_dependency_manifest_reference`, `runtime_budget_reference`, `runtime_stop_references`, `runtime_compensation_references`, `runtime_artifact_plan_reference`, `runtime_event_plan_reference`) — cada uma validada contra seu validador real já existente, nunca uma reimplementação paralela. `context` nunca é lido para nenhuma decisão; o próprio construtor deste request não aceita um segundo parâmetro para isso.

## Runtime Stages

`runtime-stage-simulation-reference.js` (47 campos exatos) materializa cada stage do `StageManifestReference` do Gateway **1:1** — mesmo `stage_type`, mesma ordem, mesmas referências de model/tool/workflow, mesmas estimativas, mesmo paralelismo/optional/approval — nunca infere, nunca zera, nunca adiciona uma referência que o stage record de origem não já declarava. `side_effect_classification` reutiliza `SIDE_EFFECT_CLASSIFICATIONS` de `execution-plan-stage.js` (por sua vez idêntico a `TOOL_SIDE_EFFECTS` da PR #93); `risk_classification` reutiliza `RISK_CLASSIFICATIONS` de `execution-authorization-scope.js`. `runtime-stage-simulation-manifest.js` (30 campos exatos) agrega essas referências preservando contagem, ordem canônica (`stage_sequence`) e fingerprint.

**O Runtime Stage Manifest preserva integralmente a semântica do Stage Manifest upstream; um self-fingerprint válido não substitui o cross-check 1:1.** (pr103fix, FIX #1) `compareRuntimeStageToSourceStage` em `runtime-execution-package.js` compara integralmente 22 campos por stage — `source_orchestrator_stage_id`, `stage_sequence`, `stage_type`, `task_reference_id`, `agent_reference_id`, `memory_selection_reference_id`, `context_assembly_reference_id`, `model_selection_reference_id`, `tool_reference_ids`, `workflow_reference_id`, `dependency_reference_ids`, `required_capabilities`, `required_modalities`, `priority`, `parallelizable`, `optional`, `approval_required`, `estimated_input_tokens`, `estimated_output_tokens`, `estimated_total_tokens`, `estimated_cost_minor_units` (arrays canonicalizados via sort antes da comparação; a ordem dos stages continua semanticamente relevante e não é canonicalizada) — qualquer divergência bloqueia com `RUNTIME_STAGE_MANIFEST_BLOCKED`/`runtime_stage_not_preserved_1to1::<stage_id>::<field>`. Os campos derivados `binding_reference_ids`/`stop_reference_ids`/`compensation_reference_ids` são recalculados a partir das fontes reais já presentes na requisição (`binding_ledger`, `runtime_stop_references`, `runtime_compensation_references`) e comparados, nunca confiados; `side_effect_classification` é cross-validado na direção "esconder uma mudança de estado real atrás de `NONE`" usando evidência real de compensação; `risk_classification` é cross-validado contra `authorization_scope_reference.allowed_risk_classifications`, a única fonte real disponível nesta camada (ver "Limitações").

**Campos `would_*` permanecem false nesta PR e não representam intenção operacional.** `stage_would_execute`, `stage_would_call_model`, `stage_would_call_tool`, `stage_would_call_workflow`, `stage_would_use_network`, `stage_would_read_memory`, `stage_would_write_memory` são `SAFE_FLAGS` forçados, junto com `stage_started`/`stage_completed`/`stage_failed`/`stage_compensated`.

## Runtime Dependencies

`runtime-dependency-simulation-reference.js` (18 campos exatos) preserva cada aresta do `DependencyGraphReference` do Gateway — id, from, to, type, required — sem nunca aplicar a dependência (`dependency_satisfied`/`dependency_applied`/`would_allow_transition` são sempre `false`). `runtime-dependency-simulation-manifest.js` (17 campos exatos) reutiliza `hasDependencyCycle` de `orchestrator-plan-dependency.js` (a mesma detecção de ciclo já usada pela PR #99) para derivar `cycle_free` honestamente, nunca assumido `true`.

**Runtime dependency endpoints são derivados do grafo upstream e não podem ser redirecionados pelo caller.** (pr103fix, FIX #2) O evaluator constrói um mapa determinístico source-stage-id → `runtime_stage_reference_id` e, para cada `DependencyRecord` de origem, valida integralmente `source_dependency_id`, `from_runtime_stage_id`/`to_runtime_stage_id` (via lookup nesse mapa — nunca por posição no array), `dependency_type` e `required` contra a aresta real correspondente, resolvendo ambos os lados por `Map` (nunca por índice), o que garante correspondência independente da ordem de entrada, cardinalidade idêntica, e detecção de qualquer endpoint redirecionado, reaproveitado ou inexistente. Qualquer divergência bloqueia com `RUNTIME_DEPENDENCY_BLOCKED`/`runtime_dependency_endpoint_mismatch::<dependency_id>` (ou `runtime_dependency_cardinality_mismatch` quando a contagem diverge).

## Runtime Budget

`runtime-budget-simulation-reference.js` (36 campos exatos) soma as estimativas reais dos Runtime Stages e compara contra os limites do `ExecutionPlanBudget` real (PR #98) — nunca reserva, nunca consome. **Nenhum token ou custo é reservado ou consumido.** `tokens_reserved`/`tokens_consumed`/`cost_reserved`/`cost_consumed` são `SAFE_FLAGS` forçados `false`; valores monetários permanecem em minor units, sem conversão, como já estabelecido pela PR #98.

**O Runtime Budget deriva seus limites do ExecutionPlanBudget real. Flags de limite fornecidas pelo caller não são fonte de verdade.** (pr103fix, FIX #3) `RuntimeExecutionSimulationRequest` ganhou o campo obrigatório `execution_budget_reference`, validado pelo contrato e validator oficiais já existentes de `execution-plan-budget.js` (`validateExecutionPlanBudget`/`buildExecutionPlanBudget`) — nenhum contrato paralelo foi criado. O evaluator cross-valida integralmente `runtime_budget_reference` contra esse `execution_budget_reference` real (`execution_budget_id`, `budget_authorization_id`, `maximum_total_tokens`, `maximum_input_tokens`, `maximum_output_tokens`, `maximum_total_cost_minor_units`, `reserved_memory_tokens`, `reserved_context_tokens`, `reserved_output_tokens`), bloqueando com `RUNTIME_BUDGET_BLOCKED`/`runtime_budget_not_linked_to_real_execution_plan_budget` em qualquer divergência. Em seguida, `model_stage_count`/`tool_stage_count`/`workflow_stage_count`/`parallel_stage_count` são recomputados contra os caps reais (`maximum_model_stages`/`maximum_tool_stages`/`maximum_workflow_stages`/`maximum_parallel_stages`) e `stage_counts_within_limit` é honestamente rederivado — nunca aceito como declaração confiada do caller — bloqueando com `runtime_budget_stage_counts_within_limit_not_honestly_derived` caso o valor declarado divirja do recomputado ou seja `true` quando algum cap real é excedido.

## Runtime Stops

`runtime-stop-simulation-reference.js` (20 campos exatos) referencia declarativamente uma `ExecutionPlanStopCondition` real (PR #98), vinculada ao plano/stage/condição/fingerprint/versão que descreve. Nenhuma condição é avaliada: `stop_condition_evaluated`/`stop_condition_triggered`/`stop_applied` são sempre `false`.

## Compensações

`runtime-compensation-simulation-reference.js` (18 campos exatos) referencia declarativamente uma `ExecutionPlanCompensationReference` real (PR #98). `compensation_planned` é sempre `true`, mas apenas como referência declarativa — nunca que a compensação de fato rodou (`compensation_executed` permanece sempre `false`). **Todo stage classificado `STATE_CHANGE_REFERENCE` exige pelo menos uma compensação válida vinculada** (`RUNTIME_COMPENSATION_BLOCKED` caso contrário) — a mesma disciplina fail-closed que já governa toda checagem cruzada deste PR. Stages `EXTERNAL_EFFECT_REFERENCE`/`IRREVERSIBLE_REFERENCE` continuam bloqueados incondicionalmente, independentemente de qualquer compensação.

## Artifact Plan

`runtime-artifact-plan-reference.js` (14 campos exatos) planeja declarativamente quais artefatos (`AUDIT_ARTIFACT_REFERENCE`, `VALIDATION_ARTIFACT_REFERENCE`, `RESULT_ARTIFACT_REFERENCE`, `SUMMARY_ARTIFACT_REFERENCE`, `TRACE_ARTIFACT_REFERENCE`) um runtime futuro produziria.

## Event Plan

`runtime-event-plan-reference.js` (14 campos exatos) planeja declarativamente quais eventos (`RUNTIME_PACKAGE_PREPARED_REFERENCE`, `RUNTIME_STAGE_PREPARED_REFERENCE`, `RUNTIME_DEPENDENCY_REGISTERED_REFERENCE`, `RUNTIME_BUDGET_VALIDATED_REFERENCE`, `RUNTIME_STOP_REGISTERED_REFERENCE`, `RUNTIME_COMPENSATION_REGISTERED_REFERENCE`, `RUNTIME_AUDIT_REFERENCE`) um runtime futuro emitiria.

**Nenhum artefato é criado e nenhum evento é emitido.** `artifact_creation_allowed`/`artifact_created` e `event_emission_allowed`/`event_emitted` são todos `SAFE_FLAGS` forçados `false`.

## Runtime Execution Package

`runtime-execution-package.js` (64 campos exatos) é um resumo compacto e autocontido — ids, fingerprints, um `package_digest` — nunca embutindo o conteúdo completo de nenhum objeto referenciado, exatamente o mesmo papel que `ExecutionGatewayPackageReference` já cumpre uma camada abaixo. O mesmo arquivo carrega `evaluateRuntimeExecutionSimulationRequest(request, context)`, o avaliador central (28 passos, análogo a `execution-gateway-boundary.js`) — não existe um arquivo `runtime-execution-boundary.js` separado; a especificação desta PR não lista um, e o avaliador pertence naturalmente ao arquivo que materializa o pacote final que ele produz.

`computeRuntimePackageDigest()` cobre, no mínimo: Gateway Decision/Result/Package, Execution Plan/Result, Stage Manifest, Dependency Graph, Binding Ledger, Validation Ledger, Runtime Stage/Dependency Manifest, Runtime Budget, `execution_budget_reference` (pr103fix, FIX #3), Stops, Compensações, Artifact Plan, Event Plan, estágios ordenados, dependency ids, estimativas, e identidade — via `computeCanonicalContentDigest`, nunca `stablePayload` bruto (ver "Correção de compounding" abaixo).

**`runtime_package_fingerprint` e `package_digest` continuam representando o mesmo SHA-256 compacto de sempre** (pr103fix): incluir `execution_budget_reference` no cálculo não muda a forma do digest — ainda um único digest SHA-256 de ~71 caracteres via `computeCanonicalContentDigest`, nunca um payload bruto embutido — apenas amplia o conjunto de conteúdo coberto por ele. Testes de regressão dedicados (`package: mutating ... changes package_digest`, `regression: package fingerprint and digest are stable across re-evaluation`) continuam verdes sem alteração de forma.

### Ordem de avaliação e precedência

A ordem real do código segue as dependências de dados: request → identidade (tenant/organization/project/session/agent/actor) → Gateway (decision/result/package) → Execution Plan/Result → Stage Manifest (origem + Runtime Stage Manifest 1:1) → Dependency Graph (origem + Runtime Dependency Manifest) → Binding Ledger → Validation Ledger → Policy (só é avaliável depois que o Runtime Stage Manifest revela os `stage_type`/`side_effect_classification` reais) → Budget → Stops → Compensações → Artifact Plan → Event Plan → Package Fingerprint → Package Digest → invariantes de não-execução → `RUNTIME_PACKAGE_PREPARED_SIMULATION`. A ordem *declarada* em `RUNTIME_PRECEDENCE_ORDER` (24 status) é uma tabela de prioridade separada — a mesma distinção "ordem de declaração ≠ ordem de avaliação" que `validation-taxonomy.js`/`execution-gateway-decision.js` já estabeleceram, não uma descrição literal da ordem em que o código executa.

### 24 status, 16 flags de validação

`RUNTIME_EXECUTION_SIMULATION_STATUSES` tem 24 valores: os 18 `RUNTIME_*` que esta PR introduz, mais `TENANT_BLOCKED`/`ORGANIZATION_BLOCKED`/`PROJECT_BLOCKED`/`SESSION_BLOCKED`/`AGENT_BLOCKED`/`ACTOR_BLOCKED` — os mesmos literais que `execution-gateway-decision.js` já usa, reutilizados verbatim ("não criar enums paralelos incompatíveis"), nunca redeclarados com prefixo `RUNTIME_`. Os 16 campos `*_validated` da decisão mapeiam 1:1 nas próprias seções de "Cross-checks obrigatórios" da especificação (Gateway, Execution Plan, Stage Manifest, Dependency Graph, Binding Ledger, Validation Ledger, Budget, Stops, Compensações, Package Fingerprint, Package Digest = 11) mais 5 procedurais (`request_validated`, `policy_validated`, `artifact_plan_validated`, `event_plan_validated`, `non_execution_invariants_validated`). `RUNTIME_PACKAGE_REFERENCE_BLOCKED` cobre tanto o cross-check do próprio `gateway_package_reference` quanto as checagens de Execution Plan/Result — esta taxonomia de 24 status não tem um status dedicado só para essas duas últimas (ver "Limitações").

## Decision, Result, Registry, Audit

`runtime-execution-simulation-decision.js` (79 campos exatos) e `runtime-execution-simulation-result.js` (68 campos exatos, envelope fino sobre a decisão) seguem exatamente a mesma forma de `execution-gateway-decision.js`/`execution-gateway-result.js`: `runtime_package_prepared_in_simulation=true` somente para `RUNTIME_PACKAGE_PREPARED_SIMULATION`; todos os 29 flags operacionais (`runtime_admitted_in_simulation`, `runtime_enabled`, `execution_authorized`, ..., `event_emitted`, `executed`) são sempre `false`, para todo status, sem exceção.

**O Runtime Execution Simulation desta implementação não inicia scheduler, job, queue, worker ou estágio.** `scheduler_started`/`job_created`/`queue_used`/`worker_started`/`stage_started` são `SAFE_FLAGS` forçados em toda a cadeia decision → result → package.

`runtime-execution-simulation-registry.js` cria 14 registros privados e sintéticos (requests, stage references, stage manifests, dependency references, dependency manifests, budget references, stop references, compensation references, artifact plans, event plans, runtime packages, decisions, results, e auditorias) — reutilizando `createEntityStore`/`resolveRegistration` exatamente como `execution-gateway-registry.js` já faz (replay, payload mismatch, conflito de versão/fingerprint, reassignment de tenant/organization). Sem persistência.

`runtime-execution-simulation-audit.js` registra somente ids, fingerprints, digest, status/decision/next_state, bindings de identidade, e 7 grupos de contadores (stage, dependency, budget, stop, compensation, artifact, event counts) — nunca payload, StageRecords completos, prompts, memória, mensagens, parâmetros de ferramenta, segredos, ou código.

## Correção de compounding de fingerprint

A mesma classe de defeito que as PRs #100 e #102 já corrigiram uma vez cada (embutir um fingerprint canônico já grande como campo simples dentro de um objeto também fingerprintado depois, comprimindo através de camadas) foi evitada nesta PR desde o início: `requestFingerprint`/`gatewayResultFingerprint`/`runtime_decision_fingerprint`/`package_digest` usam `computeCanonicalContentDigest` (digest SHA-256 fixo de ~71 caracteres) em vez de `stablePayload` bruto, em todo ponto onde um objeto já-grande (o request inteiro, ~1.5MB; a decisão, ~140KB) seria embutido em outra camada. Um cenário completo do fixture ficou em ~1.6MB (request + decision), em linha com o precedente das PRs #102/#100 — sem qualquer explosão de tamanho.

## Fixture

`test/fixtures/hermes-runtime-execution-simulation-contracts.json` (~42,6MB, em linha com o precedente das PRs #100-#102, todas entre ~22-43MB; `fixture_version: 2` desde pr103fix) contém **26 cenários curados** — um representante por camada de bloqueio, mais os 4 caminhos aceitos (sem LLM, model reference, tool reference, workflow reference), mais `budget-not-linked-to-execution-plan-budget` e `runtime-stage-memory-reference-tampered` (pr103fix, FIX #3 e FIX #1 respectivamente) — armazenando apenas `{request, decision}` por cenário. A cauda longa de mutações (organization/project/session/agent-mismatch além do tenant já coberto, model/tool/workflow/parallel-stage policy, external/irreversible effect, state-change-without-compensation, version-mismatch inerte, side-channel hostil, e as adulterações campo-a-campo de FIX #1/#2/#3) é coberta **inline** em `test/runtime-execution-simulation-contracts.test.js`, construída via `test/helpers/runtime-execution-simulation-test-data.js` — o mesmo "golden bundle" técnico já estabelecido pela PR #102, uma camada acima.

## Confirmação de nenhuma execução real

Todo novo contrato força `simulation=true`/`production_blocked=true`/`rollout_percentage=0`. `context` nunca é lido para nenhuma decisão (teste dedicado injeta um `context` hostil com `runtimeEnabled: true`/`executionAuthorized: true`/`schedulerStarted: true`/etc. e confirma zero efeito). **Nenhum agente, modelo, provider, ferramenta ou workflow é executado nesta implementação.**

## Limitações

- **`RUNTIME_PACKAGE_REFERENCE_BLOCKED` cobre tanto o cross-check do `gateway_package_reference` quanto Execution Plan/Result.** A taxonomia de 24 status desta PR não tem um status dedicado só para "Execution Plan não preparado" (diferente da PR #102, cujo `GATEWAY_STATUSES` tinha `EXECUTION_PLAN_BLOCKED`/`EXECUTION_PLAN_RESULT_BLOCKED` como status próprios) — a especificação desta PR simplesmente não listou um status equivalente entre os 18 `RUNTIME_*`. Documentado explicitamente aqui, não inventado silenciosamente.
- **`RUNTIME_DIGEST_BLOCKED`/`RUNTIME_VERSION_BLOCKED`/`RUNTIME_CONFLICT_BLOCKED` não são alcançáveis a partir deste avaliador stateless.** `package_digest` é sempre recém-computado (nunca comparado contra um valor pré-declarado pelo chamador, já que o `RuntimeExecutionPackage` não existe antes da avaliação) — `computeCanonicalContentDigest` nunca lança exceção (degrada para uma string `digest_invalid::...`), então mesmo conteúdo não serializável nunca bloqueia por essa via. `expected_runtime_registry_version` é validado estruturalmente (inteiro ≥ 1) mas nunca comparado contra nada real, pela mesma razão que `expected_gateway_registry_version` da PR #102 permanece inerte (nenhum oráculo de versão ao vivo dentro de um avaliador stateless) — ver o fix equivalente em `HERMES_EXECUTION_GATEWAY_BOUNDARY_SIMULATION.md`. Conflitos de versão/fingerprint/payload são, ao invés disso, responsabilidade real do registry com estado (`runtime-execution-simulation-registry.js`), já testada separadamente.
- **`RuntimeStopSimulationReference`/`RuntimeCompensationSimulationReference` sempre recomputam seu próprio fingerprint na construção, ignorando qualquer valor que o chamador tenha declarado** — a mesma disciplina "nunca confia no fingerprint declarado" que toda referência auto-fingerprintada deste codebase já segue desde a PR #97fix. Isso significa que "tamperar" esse campo especificamente nunca é observável como bloqueio de decisão nem como exceção de construção — apenas silenciosamente corrigido, o comportamento correto e esperado.
- **`side_effect_classification`/`risk_classification` por stage não são reexpostos pelo próprio `execution-plan-engine.js`** (são computados internamente a partir de `task_reference`/`compensation_references` da requisição original, nunca expostos no `plan`/`result` retornados). O helper de teste (`test/helpers/runtime-execution-simulation-test-data.js`) reimplementa a mesma derivação (`deriveSideEffectClassification`, idêntica à função privada homônima do engine) lendo a requisição bruta do fixture de plano diretamente — a mesma técnica já usada pela PR #102 para obter `execution_plan_budget`/`authorization_scope_reference` da requisição original.
- **`isPlainObject` (read-only-adapter-contract.js) trata `Date`/`Map`/`Set`/`RegExp` como "objeto plano"** e o scanner de material operacional (`findAgentCoreOperationalMaterial`) só percorre chaves próprias enumeráveis — nenhuma dessas quatro classes tem alguma, então passam despercebidas se escaneadas isoladamente. Gap pré-existente, fora do escopo desta PR corrigir (mudaria o scanner compartilhado por toda validação do codebase) — e nunca alcançável de qualquer forma real, já que todo campo exato desta PR é checado por tipo (`isNonEmptyString`/`Number.isInteger`/`typeof === 'boolean'`) muito antes deste scanner rodar.
